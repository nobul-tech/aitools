# S3-MdmPkg-Build notes: how build-deploy.sh builds deploy/, and how big each script is

Delegate: S3-MdmPkg-Build (for S3-MdmPkg). Date: 2026-10-26. Read-only on both repos.
Everything was measured by building in new worktrees, with an isolated HOME and TMPDIR,
into a `git clone` of the dotprofile. The real HOME and `/Users/new-jose/repos/aitools-nobul-jose`
were not written: its `git status --short` afterwards shows only a `sessions/.DS_Store` change, which
was already there.

## 0. Headline

1. **The committed dotprofile `deploy/` is stale.** HEAD `525ee49` has the same 42 files with the same
   blob ids as `825aed4` (`git ls-tree -l` output is identical). These files have no deploy-harness, no
   `setup-user-config`, `aitools-profile` or `aitools-json` copies, and no embedded resolver
   (`grep -c "Embedded profile resolver"` = 0 in setup-user-claude.sh/.ps1 and setup-user-settings.sh).
   A build from aitools main `480b901` writes **50 files**, and 14 of them (7 .sh + 7 .ps1) are 200,000 B or more.
2. **Every generated script carries the whole library inline.** That is aitools-lib.sh at 140,653 B or
   aitools-lib.ps1 at 154,937 B. So the smallest generated .ps1 is about 155 KB, which leaves at most
   about 45 KB of headroom under Intune's Windows 200 KB limit for any tool.
3. **Six .ps1 files are over 200 KB on every ref I built (main, #106, #111, #112):**
   setup-user-claude, -cursor, -settings, -skills, -hooks, plus aitools-profile.ps1. deploy-harness.ps1
   is a seventh, except on #111. #111 fixes only deploy-harness (2.31 MB down to 190,907 B), and does it
   by adding a 2,085,269 B sibling data file. **No .sh is over 1 MB** except deploy-harness.sh (2.28 MB)
   when it is built without #111.
4. **deploy/ is not one self-contained file per tool.** deploy-harness reads three sibling files at run
   time (four with #111), and setup-user-config reads two. No manifest or entry point runs the set. The
   only ordering is in comments: "Run it FIRST in an MDM sequence".

## 1. How build-deploy.sh builds deploy/ (aitools main 480b901)

All references are to `/Users/new-jose/repos/aitools/scripts/build-deploy.sh` on main.

**Target and inputs**
- The output goes into the **dotprofile**, not the aitools repo: `DEPLOY_DIR="$_urp/deploy"` (L218).
- `_urp` comes from `AITOOLS_USER_REPO_PATH` when it is set (L188). Otherwise a child bash runs
  `resolve_user_repo_path` from aitools-lib.sh (L195-202).
- With no dotprofile, or a resolver error, the build is skipped with exit 0 (L203-217).
- The build is staged in `$BUILD_TMP/deploy` (L616-618). At the end it runs `rm -rf "$DEPLOY_DIR_FINAL"`
  and then `mv` (L2298-2305). A failed build therefore leaves the old deploy/ in place, but a
  successful one deletes and replaces the whole directory. This is why it must never run against the
  real dotprofile.
- node is required. Without it the build is skipped with exit 0 (L86-89); node parses the hooks manifest.
- pwsh, when present, validates every generated .ps1 with ParseFile (L2225-2282).
- All .ps1 files are converted to CRLF (L2294).

**Mechanisms**
- **`inline_lib_bash` / `inline_lib_ps1`** (L124-173): perl replaces the *first* line that sources
  `aitools-lib.sh`, or dot-sources `aitools-lib.ps1`, with the full library text. When a BLOCK_FILE
  argument is given, that block's content follows the library. If no such line exists, the build fails.
- **Body markers**: `extract_between FILE START END [--crlf]` (L335-357) uses a perl flip-flop and
  excludes the marker lines. The markers used are:
  - `# --- BEGIN/END preamble` (setup-user-claude, L648)
  - `cursor body` (L836)
  - `mcp body` (L1205)
  - `settings body` (L1235)
  - `skills body` / `BEGIN skill discovery` (L1265)
  - `hooks body` / `BEGIN hook deployment` / `END hook deployment` (L1472, L1532)
  - `BEGIN/END exit` (everywhere)

  `extract_span` (L365-398) cuts on section headings. deploy-harness uses it on main
  (`^# 3\. The six directories` ... EOF, L2040). `replace_once` (L403-415) makes the one adopt-target
  substitution in deploy-harness (L2041).
- **Embedded profile resolver** (L417-608, marker `# --- Embedded profile resolver (generated by
  build-deploy.sh; M3 B5) ---`):
  - It holds build-time copies of `aitools-profile.sh`, `aitools-lib.sh` and `aitools-json.pl` (or the
    three .ps1 equivalents), as heredocs (sh) or `|`-prefixed here-strings (ps1).
  - At run time they are written to a private temp dir, and `AITOOLS_PROFILE_SH` / `_PS1` points at it.
  - The "claude" variant adds the dotprofile `claude/CLAUDE.md`, `shared/claude-shared.md`, a
    profile.json snapshot and every dotprofile `claude/rules/*.md` (L511-522, L559-570).
  - It is appended after the inlined lib in setup-user-claude (claude variant, L707/L803), and in
    setup-user-cursor (L866/L907) and setup-user-settings (L1239/L1251).
  - A post-build check requires exactly one copy in each of those six files (L2210-2218).
  - **Consequence: these six scripts carry the library twice**, once inlined and once as the resolver's
    copy.
- **Skills** (L1255-1449): every `shared/skills/*/SKILL.md` is `cat`-ed into a heredoc (sh,
  `__SKILL_<NAME>__`) or into a `@' '@` here-string (ps1), plus one `deploy_embedded_skill` call per
  skill for each of the two destinations (~/.claude/skills and ~/.cursor/skills). The adopt target is "".
- **Hooks** (L1452-1632): every file in `hooks-manifest.json` (hooks plus `deploy` helpers, from
  shared/hooks/ or else scripts/) is embedded as a heredoc `__EMB_<FILE>__`. `REGS_JSON` is built from
  the manifest at build time (L1523-1526), and the merge section is extracted by markers.
- **Plain tool scripts** (setup-bash, -cursor-ide-mcp, -datadog, -gh-cli, -go, -google-chrome, -modal,
  -pandoc, -perl, -python, -rust, -typst, -uv, -vercelcli, -user-shell): a header line, then
  `tail -n +2 scripts/X.sh | inline_lib_bash` (for example L919, L927; L938-1193). The output is the
  source script plus the library and nothing else.
- **cursor**: the body is extracted whole. `subst_cursor_defaults` swaps in the build-time
  `cursor.cli` vimMode and model defaults (L820-845).
- **Copied with lib inlined** (L1642-1673): setup-user-config.sh/.ps1 and aitools-profile.sh/.ps1.
  aitools-json.pl/.ps1 are copied as they are.
- **deploy-harness** (L1675-2203, main):
  - The source dirs are parsed from `scripts/deploy-harness.sh` `add_source` lines (L1711-1735). There
    are 9 calls (deploy-harness.sh:254-263): reference, registries, shared/hooks, .claude/hooks,
    shared/skills, .claude/skills, shared/rules, .claude/rules and dotprofile claude/rules. The bin CLIs
    come from its `for cli in harness-db.py read-session.py read-session-full.py` line (L1737, :266).
  - Each listed file is base64-encoded with its size and sha256 (`mdm_emit_payload`, L1868-1895), and
    **inline in the script** on main.
  - My build log: "Harness snapshot: 134 files from 8 source directories (+ bin)", with .claude/hooks
    not found (`run-main/build.log` L59-60).
  - The end marker `# --- END OF GENERATED SCRIPT (deploy-harness.sh) ---` guards against truncation
    (L1962, L2043).

**Run-time dependence on other files.** The scripts do not depend on the repos at run time. They do
depend on these:
- deploy-harness.sh/.ps1 call `$SCRIPT_DIR/setup-user-config.sh` (deploy-harness.sh:99; build-deploy
  header L1905-1906: "Ships with its deploy/ directory: the config.json writer it calls ... sits
  beside it").
- setup-user-config.sh reads `$SCRIPT_DIR/aitools-profile.sh` and `$SCRIPT_DIR/aitools-json.pl`
  (generated file, run-pr111 L3160-3161).
- With #111, deploy-harness also needs `$SCRIPT_DIR/deploy-harness.payload`.
- The `$SCRIPT_DIR/aitools-lib.sh` reference in generated setup-user-claude.sh (L3164) is inside the
  embedded aitools-profile.sh heredoc (L3095-4659), and resolves to the private temp dir. It is not a
  sibling dependency.
- External tools are needed at run time: node (hooks merge, cursor), perl (JSON engine, deploy-harness
  unpack) and git (the deploy-harness passthrough, L2004-2015).
- Some outputs depend on state that another script writes. setup-user-cursor fans out
  `~/.aitools/rules`, which deploy-harness fills (L855, L895). deploy-harness needs the bootstrap keys
  in `~/.aitools/config.json` that `aitools-install` writes (L1916-1919).

## 2. Sizes

Thresholds: Intune Windows script "< 200 KB", Intune macOS script "< 1 MB", as quoted in PR #111.
I flag a file at 200,000 B and 1,000,000 B, the same values #111's build check uses
(pr111 build-deploy.sh:2474). Whether Intune means 200,000 or 204,800 is unknown, and it changes no
flag below except possibly aitools-profile.sh (216,961, over either way).

**Commands**
- Committed: `git -C /Users/new-jose/repos/aitools-nobul-jose ls-tree -l HEAD deploy/`, and the same at
  `825aed4`.
- Built: `.claude/worktrees/mdmpkg/.scratch/session-mdmpkg/build/measure.sh <label> <ref>`. The script:
  - adds a detached worktree `.claude/worktrees/mdmpkg-b-<label>`;
  - runs `git clone` of the dotprofile into `run-<label>/dotprofile`;
  - runs `env HOME=run-<label>/home TMPDIR=run-<label>/tmp AITOOLS_USER_REPO_PATH=run-<label>/dotprofile
    bash <wt>/scripts/build-deploy.sh`;
  - then runs `ls -l` on the output.

  All four builds exited 0. The outputs are in `run-*/sizes.txt`.

## 3. What the open PRs change in deploy/

- **#106** (feature/harness-hookin, 0dea75f): no change to build-deploy.sh or to any embedded source.
  It changes the installer and the `aitools` loop (PR file list). Measured: the same files and sizes as
  its base. It is relevant to MDM only because it makes deploy-harness part of every dev run; it does
  not change the deploy/ layout.
- **#111** (feature/harness-mdm-followups, 8caa79e; stacked on #100):
  - It moves the harness snapshot into **`deploy/deploy-harness.payload`** (ASCII, LF, a record per file
    with `<path>\t<exec>\t<size>\t<sha256>` and base64 lines). The scripts embed only the payload's
    sha256 (pr111 build-deploy.sh:1698-1702, :1890-1927, :2034).
  - It switches deploy-harness extraction to `# --- BEGIN/END <name> ---` markers.
  - It adds `--skip-config` and the no-bootstrap n/a path.
  - It makes the build fail at ps1 ≥200,000 B or sh ≥1,000,000 B, **for deploy-harness only**
    (pr111:2473-2483).
  - It fixes the BUILD_TMP trap leak.
  - Measured result: .sh 177,181 B and .ps1 190,907 B (4.5% headroom), plus the 2,085,269 B payload.
    The other 48 files are unchanged against #106.
- **#112** (fix/mf-audit-claude-build, 52821bd; stacked on #103):
  - It changes the generated setup-user-claude/-cursor/-settings .ps1, which now end with
    `} finally { Remove-AitoolsEmbed }`, and adds build-output colour handling.
  - It carries #103's aitools-lib.sh +114 lines and aitools-lib.ps1 +136 lines (PR file list). Because
    the lib is in every script, **every generated file grows by about 6.0 KB (.sh) and 6.7-7.2 KB
    (.ps1)**, and the scripts that carry the lib twice grow twice that.
  - Measured: the largest plain .ps1 goes from 174,656 to 181,892 (setup-user-config.ps1). The
    smallest .ps1 is 163,029, which leaves about 37 KB of headroom.
  - Any lib growth now cuts the 200 KB headroom of every Windows script.
- **Not measured:** the combination #111 + #112, and #100 alone. Inferred: #111+#112 would put
  deploy-harness.ps1 at about 190,907 + ~7,200 = ~198 K, within 1% of the 200,000 B fail line that #111
  adds. The build would probably warn, and could fail with any further lib growth.

## 4. Single self-contained file per tool, or a directory?

- **There is no single-file assumption in the code.** On main, deploy-harness already needs
  setup-user-config + aitools-profile + aitools-json beside it (L1639-1673, L1905-1906). #111 adds the
  payload, and its PR text says: "An MDM deploys the whole `deploy/` directory, not a single uploaded
  script ... On Intune this means a Win32 app or macOS package that carries the directory ... the
  packaging is not decided."
- The other 38 setup scripts are single-file self-contained apart from external tools and the state
  ordering (section 1). But 6 of them (the .ps1 of setup-user-claude, -cursor, -settings, -skills, -hooks, and the aitools-profile helper) are over 200 KB on Windows, so they cannot be Intune
  "PowerShell scripts" either, whatever the directory question.
- **There is no manifest or entry point.** There is no run-all script in deploy/ (the 50 files
  listed), and no order list in build-deploy.sh or deploy-paths.md. The only ordering is in comments:
  - build-deploy.sh L855 / L895: "Run deploy-harness.sh first";
  - L1913 / L2063: "Run it FIRST in an MDM sequence";
  - the deploy-harness bootstrap requirement (L1916-1919).

  The dev-path order is in `scripts/aitools` deploy_configs and `aitools-install` (#106), not in deploy/.

## INCIDENTs

- INCIDENT: the committed dotprofile `deploy/` (525ee49 = 825aed4) lags aitools main.
  - It lacks 8 of the 50 files main generates: deploy-harness.sh/.ps1, setup-user-config.sh/.ps1,
    aitools-profile.sh/.ps1, aitools-json.pl/.ps1.
  - It lacks the M3 B5 embedded resolver.
  - An MDM package built from the committed deploy/ would ship the pre-harness, pre-resolver scripts.
  - (PR #111 and #112 report this as the known check-pre-push step 7 FAIL.)
- INCIDENT: there is no size gate for any generated script except deploy-harness (#111 adds a gate for
  that one only). On main, 7 generated .ps1 (and 7 .sh) are 200,000 B or more (setup-user-claude, -cursor,
  -settings, -skills, -hooks, aitools-profile, deploy-harness), and the build passes silently.
- INCIDENT: the library is embedded twice in setup-user-claude/-cursor/-settings, once inlined
  (`inline_lib_*`) and once as the resolver's file copy (`RESOLVER_SH_FILES`, L436-437). That is
  ~281 K of 431 K (sh) and ~310 K of 464 K (ps1). Getting these under 200 KB needs either one shared
  copy, or the resolver files as sibling files.
- INCIDENT (fixed by #111, still on main): `trap 'rm -rf "$MDM_TMP"' EXIT` (L1706) replaces
  `trap _cleanup_build_tmp EXIT` (L320), so BUILD_TMP leaks on every build.
- INCIDENT: there is no MDM run-order manifest. The order (deploy-harness first, after aitools-install
  bootstrap) is only in generated-script comments.
