## (A) Running IntuneWinAppUtil.exe on macOS/Linux via Wine, Mono or .NET

### Takeaway
Under Wine plus `winetricks dotnet48`, the unmodified exe works on Linux by community report only (Debian, Fedora, Arch; Ubuntu 22.04 after a fix). Microsoft says nothing about it. I found no report of it working on macOS. I found no working report for Mono on its own, no Docker image that bundles Wine and the tool, and no WineHQ AppDB entry. A decompiled port is barred by licence 4(b). The licence does not mention emulation or operating systems. Redistributing the exe in a Docker image, package or repo is barred by 4(e), and at least one popular community repo commits the exe anyway.

### Inferences
- **Licence and Wine.** No clause forbids running the unmodified exe under Wine on Linux: clause 1 allows "any number of copies", and nothing restricts the platform. Clause 4(a), "work around any technical limitations", is ambiguous. It most plausibly targets bypassing limits built into the software, not running it on another OS. But a cautious reader could argue that Windows-only targeting is a "technical limitation". Commander or legal call.
- **Licence and patching.** Patching the binary, which the earlier Probe did, is a much clearer conflict with 4(a)/(c). Decompiling or porting it is a clear conflict with 4(b). A "port of IntuneWinAppUtil" is permissible only as a clean-room reimplementation, which is a different tool, not "the official exe on Linux".
- **Docker images.** A Docker image that bundles the exe and is pushed to any registry, public or shared, would "share, publish" it, which 4(e) forbids. A private build-time image layer that fetches the exe at run time and is never pushed avoids this. Exposing such an image as a service would hit the "stand-alone hosted offering" clause of 4(e).
- **Operational fit of Wine is poor for this script.** It works only on x86_64 Linux; no evidence exists for macOS arm64, where Wine would need Rosetta or a Wine-on-ARM translation layer. `winetricks dotnet48` runs an interactive .NET Framework installer ("Follow the installation prompts"). Results vary by distribution (Ubuntu 22.04 needed wine-mono). It downloads hundreds of MB of Microsoft .NET redistributables, which carry their own licence. And it is unsupported by Microsoft. Claude Code web and Cursor cloud VMs are x86_64 Ubuntu, so Wine is technically conceivable there, but heavy and fragile. Not recommended.
- **The redistribution examples show that 4(e) is commonly ignored.** That is no reason for aitools to copy them. The lure repos are a hard block (impersonation/typosquat), and build-package must only fetch from `microsoft/Microsoft-Win32-Content-Prep-Tool` at a pinned commit with our SHA-256.

### Gaps
- I found no first-hand report of Mono alone, without Wine, running IntuneWinAppUtil. The 2020 "Wine and Mono" Debian report does not say whether Mono meant the standalone runtime or wine-mono. Whether standalone Mono loads an x64-only PE32+ that targets .NET Framework 4.7.2: unknown.
- No WineHQ AppDB entry was found. I did not browse appdb.winehq.org directly (search only).
- No public Docker image that bundles Wine and the tool was found. Absence is not proven.
- Whether the tool sends telemetry under clause 3: unknown.
- I have not read a legal opinion on how 4(a) applies to Wine.

## (B) Hosted Windows CI runners: GitHub Actions, Azure DevOps, GitLab

### Takeaway
GitHub-hosted `windows-2022` and `windows-2025` (x64) are GA as of 2026-10-26. windows-2019 was retired by 2025-06-30. No windows-2022 deprecation is announced. Standard runners are free in public repos; nobul-tech/aitools is PUBLIC. For private repos, Windows 2-core x64 costs $0.010/min after the plan's included minutes. The exe can, and should, be fetched at build time from Microsoft's GitHub at a pinned commit. No official Microsoft GitHub Action exists for it. Community workflows exist, and one vendors the exe. Azure DevOps offers windows-2022/2025 with a 1,800-minute free tier for private projects. GitLab's hosted Windows runners are still Beta.

### Inferences

## (C) Triggering a Windows build from the CLI, and what it means for Claude Code web / Cursor cloud

### Takeaway
Yes. A non-Windows developer can run `gh workflow run <file> --ref <ref> -f version=...`, then `gh run download <run-id> -n <artifact>`. Both are REST-based `gh` subcommands. The workflow file must exist on the default branch. For Claude Code web, `gh` REST calls go through the GitHub proxy for attached repos with no token of your own. Whether that proxy's scoped credential allows `actions:write` (dispatch), and whether the artifact blob-storage redirect host is allowlisted, is unknown. Cursor cloud agents have internet access by default, but their `gh` authentication for Actions is not documented.

### Cited Findings
- `gh workflow run`: "Create a `workflow_dispatch` event for a given workflow ... The given workflow file must support an `on.workflow_dispatch` trigger". It takes `-r, --ref`, `-f/--raw-field` and `-F/--field` inputs. — `gh workflow run --help`, gh 2.103.0 (2026-10-21); [cli manual](https://cli.github.com/manual)
- `gh run download [<run-id>] [-n name] [-D dir]`: "Download artifacts generated by a GitHub Actions workflow run." — `gh run download --help`, gh 2.103.0
- "This event will only trigger a workflow run if the workflow file exists on the default branch. ... Once a workflow has run at least once, you can dispatch it against any branch or tag via the GitHub API or GitHub CLI." — [Events that trigger workflows](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows)
- "Anyone with write access to a repository can run actions. Any costs of running the actions are billed to the repository owner." — [GitHub Actions billing](https://docs.github.com/en/billing/concepts/product-billing/github-actions)
- **Claude Code web.** "each session gets a fresh virtual machine (VM) running Ubuntu 24.04 on x86_64". "all GitHub operations go through a dedicated proxy". The proxy "serves GitHub API requests for the repositories attached to the session. An API request for another repository gets a 403". "the proxy rejects requests to GitHub's GraphQL endpoint ... `gh` subcommands that use GraphQL, such as `gh pr` and `gh issue`, get the same 403". "`gh` subcommands that use the REST API, such as `gh workflow list`, work too." "`gh api` calls for attached repositories work without a token of your own, but a script that reads `GITHUB_TOKEN` directly gets the placeholder". "Committed files from public repositories arrive through `raw.githubusercontent.com` ... in the default Trusted list". — [Claude Code cloud environments](https://code.claude.com/docs/en/cloud-environments.md)
- **Cursor cloud.** "The agent has internet access by default. You can configure network egress controls". "Only git traffic uses the proxy. Other requests from the agent, including GitHub API calls and gh, come from the Cloud Agent ranges." The Cursor GitHub app gets "read-write privileges ... to clone the repo and make changes". — [Cursor Secrets & Network](https://cursor.com/docs/cloud-agent/security-network)

### Inferences
- **build-package.sh on macOS/Linux, `intune` kind requested.** The script can offer a documented remote path instead of a bare ERROR: `gh workflow run package.yml --ref <tag> -f kind=intune`, then `gh run watch` and `gh run download`. Alternatively the script keeps reporting `ERROR + ACTION "build on Windows (CI job intune)"` and prints these commands. That keeps the official exe on Windows and adds no emulation.
- **On Claude Code web,** dispatch and download should work if the proxy's scoped credential includes Actions write and artifact access, and if the artifact zip redirect host (GitHub artifact blob storage) passes the security proxy. Both are untested. Also, the `gh run list` / `gh run view` commands should be checked for GraphQL use before relying on them.
- **On Cursor cloud,** `gh` would need a token in a Cursor Secret (for example `GH_TOKEN` with `actions:write`). The Cursor GitHub app's permissions are for clone and push, and nothing documents that they extend to `gh`.
- Since nobul-tech/aitools is public, any collaborator with write access can trigger the job, and it costs $0.

### Gaps
- The scoped credential behind the Claude Code web GitHub proxy: whether it can POST `/actions/workflows/{id}/dispatches` and follow artifact download redirects. Unknown. Needs a live test in a web session.
- Cursor cloud's default `gh` authentication: undocumented in the pages I read.
- Whether `gh run watch` / `gh run view` use GraphQL, which the Claude Code web proxy blocks: not checked.

## (D) Self-hosted alternatives: a Windows VM on a Mac (UTM/Parallels, Windows 11 on Arm) and Windows containers

### Takeaway
Microsoft authorises Parallels Desktop 18/19/20 for Arm Windows 11 Pro/Enterprise on Apple M1-M3, and says x64 apps run under emulation there. Windows 11 on Arm emulates user-mode x64 apps (Prism, 24H2). So the x64 .NET Framework exe should run in principle. But 1.8.7 has an ARM-specific history: #159 reported a fatal encryption error, and Microsoft says it is "fixed in the latest release". I found no confirmation of it running on Arm. UTM is not on Microsoft's authorised list. Windows containers need a Windows host, so they do not help on macOS/Linux.

### Cited Findings
- "Parallels® Desktop versions 18, 19, and 20 are authorized solutions for running Arm® versions of Windows 11 Pro and Windows 11 Enterprise in a virtual environment on its platform on Apple M1, M2, and M3 computers." "you can also use apps in x64 or x86 emulation on Mac M1, M2, and M3 computers." "A unique license is required for each instance of Windows 11 Pro, either on hardware or in a virtual machine." Windows 365 Cloud PC is the other listed option. — [Microsoft Support: Windows 11 on Mac with Apple M-series](https://support.microsoft.com/en-us/windows/options-for-using-windows-11-with-mac-computers-with-apple-m1-m2-and-m3-chips-cd15fd62-9b34-4b78-b0bc-121baa3c568c)
- "Windows 11 on Arm supports emulation of both x86 and x64 apps. Performance is enhanced with the introduction of the new emulator Prism in Windows 11 24H2." "emulation only supports user mode code and doesn't support drivers." "For x64 apps, there's no WOW64 layer ... system binaries are compiled as Arm64X PE files". — [How emulation works on Arm](https://learn.microsoft.com/en-us/windows/arm/apps-on-arm-x86-emulation)
- #159 "Version 1.8.7 Does not work In ARM devices" (closed): "it now gives a fatal error on Windows ARM. Version 1.8.6 and bellow works wihtout problems ... ### Inferences
- **A Parallels Windows 11 Arm VM on the commander's Mac is a licence-clean, official-tool route.** It is the unmodified exe on Windows under Microsoft-authorised virtualisation. But it costs a Parallels licence plus a Windows 11 Pro licence. It is manual, not CI. It is not usable from Claude Code web or Cursor cloud. And it is unproven for 1.8.7 on Arm (#159). It is a reasonable "local Windows build" option for the commander only after a Phase-2 test. UTM works technically, but Microsoft does not list it as authorised.
- **Windows containers** (Server Core images) run only on Windows hosts. They give no route from macOS or Linux, and on a Windows host the exe runs natively anyway. This is general knowledge; I read no source on it in this pass.
- **Ranking for a script that must work from macOS, Windows, Linux, Claude Code web and Cursor cloud:**
  1. Native Windows host or GitHub-hosted `windows-2022` with the official exe fetched at a pinned commit. Licence-clean and $0 for a public repo.
  2. Remote trigger from any non-Windows environment via `gh workflow run` / `gh run download` (needs network plus `gh` auth with Actions write).
  3. A Parallels Arm VM for local Mac builds (test first).
  4. Wine on x86_64 Linux: community-only, fragile, 4(a) ambiguous. Not recommended.
  5. Mono, a .NET port or a patched binary: no evidence, or licence-barred. Ruled out.
