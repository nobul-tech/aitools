## 1. Exact structure of .intunewin, and which parts Microsoft documents

### Takeaway
A `.intunewin` is an unencrypted ZIP (entries Stored) holding `IntuneWinPackage/Contents/IntunePackage.intunewin` (a ZIP of the source folder, encrypted as `HMAC-SHA256[32] | IV[16] | AES-256-CBC/PKCS7 ciphertext`) and `IntuneWinPackage/Metadata/Detection.xml` (cleartext keys and metadata). Microsoft documents only the encryption parameters (Graph `fileEncryptionInfo`) and gives the cipher layout as MIT sample code; the container, the inner ZIP and the `Detection.xml` schema are documented only by the community (and implicitly by Microsoft's sample that reads them).

### Cited Findings

**Microsoft-documented (official):**
- Graph `fileEncryptionInfo` properties, verbatim: "encryptionKey — The key used to encrypt the file content."; "initializationVector — ... Must be 16 bytes."; "mac — The hash of the concatenation of the IV and encrypted file content. Must be 32 bytes."; "macKey — The key used to compute the message authentication code of the concatenation of the IV and encrypted file content. Must be 32 bytes."; "profileIdentifier — ... Currently, only ProfileVersion1 is supported."; "fileDigest — The file digest prior to encryption. ProfileVersion1 requires a non-null FileDigest."; "fileDigestAlgorithm — ProfileVersion1 currently only supports SHA256". Page "Last updated on 09/13/2024". It does not name the cipher, mode, padding, key length or byte layout. — [Graph fileEncryptionInfo](https://learn.microsoft.com/en-us/graph/api/resources/intune-apps-fileencryptioninfo?view=graph-rest-1.0)
- The commit action takes only `fileEncryptionInfo` in the body and says "A PowerShell script example of the file upload process using the ProfileVersion1 encryption scheme can be found at https://aka.ms/fileencryptioninfo." (page updated 10/10/2025). — [Graph commit action](https://learn.microsoft.com/en-us/graph/api/intune-apps-mobileappcontentfile-commit?view=graph-rest-1.0)
- That link is dead: `curl -sI https://aka.ms/fileencryptioninfo` returned `302` to `https://www.bing.com?ref=aka&shorturl=fileencryptioninfo` on 2026-10-26 (command output). So the official pointer to the ProfileVersion1 spec-by-example is broken.
- Learn on the container, only in prose: "The tool converts application installation files into the .intunewin format."; "The Microsoft Win32 Content Prep Tool zips all files and subfolders when it creates the .intunewin file."; `-c <setup_folder>` "All files in this folder are compressed into an .intunewin file."; "For the MSI setup file, this tool retrieves required information for Intune." No layout, no schema. (Last updated 04/14/2026.) — [create-win32-package](https://learn.microsoft.com/en-us/intune/app-management/deployment/create-win32-package)
- Cipher layout as MIT sample code (Microsoft, not a spec): `macOS_Application_PKG_Add.ps1` `EncryptFileWithIV` writes `hmacLength + IV.Length` zero bytes, encrypts with `[System.Security.Cryptography.Aes]::Create()` and `CreateEncryptor($encryptionKey, $initializationVector)`, then seeks to `$hmacLength`, computes `HMACSHA256` over the rest, seeks to 0 and writes the HMAC (grep lines 380-422). — microsoft/mggraph-intune-samples `LOB_Application/macOS_Application_PKG_Add.ps1` @ `2e66845`
- Microsoft's Win32 sample *reads* the community-described container: "The script extracts the detection.xml file from the .intunewin file and uses the information to create the app in Intune"; it maps `$DetectionXML.ApplicationInfo.EncryptionInfo.EncryptionKey|macKey|initializationVector|mac|fileDigest|fileDigestAlgorithm` into the commit body and reads `ApplicationInfo.MsiInfo.MsiExecutionContext|MsiProductCode|MsiProductVersion|MsiPublisher|MsiRequiresReboot|MsiUpgradeCode` (lines 25, 137-163, 229-236). — microsoft/mggraph-intune-samples `LOB_Application/Win32_Application_Add.ps1` @ `631eea2`

**Community-documented (reverse-engineered / re-implemented):**
- Outer layout, from renaming the official output to .zip: `IntuneWinPackage/Metadata/Detection.xml` and `IntuneWinPackage/Contents/IntunePackage.intunewin`; "The top .intunewin file is a zip file, which is not encrypted"; the inner file "is actually encrypted". Author: "All details about this tool are gained by thorough analysis of publicly available data." — [svrooij, Analysing Win32 Content Prep Tool (2023-10-04)](https://svrooij.io/2023/10/04/analysing-win32-content-prep-tool/)
- A real `Detection.xml` from the official tool (ToolVersion 1.8.4.0), quoted verbatim in that post: root `<ApplicationInfo xmlns:xsi="http://www.w3.org/2001/XMLSchema-instance" xmlns:xsd="http://www.w3.org/2001/XMLSchema" ToolVersion="1.8.4.0">` with children `Name`, `UnencryptedContentSize`, `FileName` (`IntunePackage.intunewin`), `SetupFile`, `EncryptionInfo` { `EncryptionKey`, `MacKey`, `InitializationVector`, `Mac`, `ProfileIdentifier` (`ProfileVersion1`), `FileDigest`, `FileDigestAlgorithm` (`SHA256`) }, all binary values base64. Re-running the tool changes key/MacKey/IV/Mac but "The FileDigest and FileDigestAlgorithm stay the same." Sizes in that sample: inner encrypted file 5,957,072 bytes vs `UnencryptedContentSize` 5,957,009. — [same post](https://svrooij.io/2023/10/04/analysing-win32-content-prep-tool/)
- Schema as implemented by ContentPrep: `[XmlRoot("ApplicationInfo")]` with attribute `ToolVersion`, elements `Name`, `Description`, `UnencryptedContentSize` (long), `FileName`, `SetupFile`, `EncryptionInfo`; `MsiApplicationInfo` subtype adds `MsiInfo`. `EncryptionInfo` element order: `EncryptionKey, MacKey, InitializationVector, Mac, ProfileIdentifier, FileDigest, FileDigestAlgorithm`. — svrooij/ContentPrep `Models/ApplicationInfo.cs`, `Models/FileEncryptionInfo.cs` @ `5468585`
- `MsiInfo` element set (ContentPrep): `MsiProductCode, MsiProductVersion, MsiPackageCode, MsiPublisher, MsiUpgradeCode, MsiExecutionContext, MsiRequiresLogon, MsiRequiresReboot, MsiIsMachineInstall, MsiIsUserInstall, MsiIncludesServices, MsiIncludesODBCDataSource, MsiContainsSystemRegistryKeys, MsiContainsSystemFolders`. ContentPrep does not read MSIs itself ("this code does not load this data from the MSI file"; "TODO: Add support for reading info from MSI files, but has to be cross platform"). — svrooij/ContentPrep `Models/MsiInfo.cs`, `Packager.cs` @ `5468585`
- Encryption (ContentPrep `Encryptor.cs`): 32-byte AES key and 32-byte HMAC key from `Aes.Create().GenerateKey()`, IV from `Aes.Create().IV` (16 bytes); `FileDigest` = SHA-256 of the *unencrypted inner ZIP*; output = 32 zero bytes + IV, then `CryptoStream` with `aes.CreateEncryptor(key, iv)` (.NET defaults), `FlushFinalBlock`, then HMAC-SHA256 over bytes [32..end] (IV + ciphertext), written at offset 0; constants `ProfileVersion1`, `SHA256`. — svrooij/ContentPrep `src/SvR.ContentPrep/Encryptor.cs` @ `5468585`
- IntuneAppBuilder implements the identical scheme independently (32-byte key and HMAC key, `Aes.Create().IV`, zero header of `hmacLength + IV.Length`, CBC via `aes.CreateEncryptor`, HMAC over [32..end], `FileDigest` = SHA-256 of the source/intermediate ZIP). — simeoncloud/IntuneAppBuilder `Source/IntuneAppBuilder/Services/IntuneAppPackagingService.cs` @ `2144de7`
- Kieselbach's decoder: unzips outer, reads `Detection.xml` `FileName`, `EncryptionKey`, `InitializationVector`, skips the first 48 bytes ("skip first 48 bytes... some IV stuff there which is not necessary for the archive"), AES-decrypts the rest; it never checks the HMAC. — okieselbach/Intune `IntuneWinAppUtilDecoder/IntuneWinAppUtilDecoder/Program.cs` @ `d8ad929`

### Inferences
- Padding is PKCS7 and the mode is CBC: all three C# implementations use .NET `Aes.Create()` defaults (CBC, PKCS7 per .NET docs as cited in the earlier findings file; I did not re-read the .NET API page). Independent arithmetic check against the official tool's output: 5,957,009 mod 16 = 1, so PKCS7 adds 15 bytes; 5,957,009 + 15 + 32 (HMAC) + 16 (IV) = 5,957,072, exactly the size svrooij measured. This rules out CTR/no-padding for the official tool (maxihafer/content-prep's "AES-CTR" README claim, noted in the earlier findings, is contradicted).
- `UnencryptedContentSize` is the size of the inner ZIP before encryption, not the source folder size (ContentPrep sets it from the ZIP file length; Microsoft's sample passes it as Graph `size`).
- The IV is stored twice (file header bytes 32-47 and `Detection.xml`); decoders differ in which copy they use (Kieselbach: XML; ContentPrep: header).
- The official tool's inner ZIP appears deterministic (same `FileDigest` across runs per svrooij), so it likely fixes timestamps; community packers do not claim this. Unknown whether Intune cares (no evidence it does).
- **Re-check of the earlier findings file** (`plans/build-package/mdm-windows-tool-findings.md` 3.2): its claim "Microsoft documents the encryption and the Graph upload; the container is community-documented only" is **upheld with a correction**: Microsoft documents the encryption *parameters and sizes*, not the algorithm; the algorithm/layout is official only as MIT sample code, and the official doc's link to that sample (aka.ms/fileencryptioninfo) is dead as of 2026-10-26. "Must be 32 bytes" for the key is not on the Learn page (it states 32 bytes only for mac and macKey); the 32-byte encryptionKey requirement in the earlier file rests on a service error string, which I did not re-verify.
- Documentation verdict: encryption = officially parameterised + official sample code (good); container/`Detection.xml`/inner ZIP = reverse-documented, but consistent across 4 independent implementations and implicitly confirmed by Microsoft's own sample parsing those element names.

### Gaps
- No Microsoft spec names AES-256-CBC/PKCS7 in prose; I found none.
- The official tool's inner-ZIP compression level, entry ordering, timestamps, and whether it writes directory entries: unknown (closed source; I did not inspect any binary output myself).
- Whether `-a` (catalog folder, "Add catalog support for Win10 S" in 1.6) adds anything to `Detection.xml`: unknown.
- Which MSI fields the official tool actually emits (ContentPrep's list includes `MsiPackageCode`, `MsiRequiresLogon` etc.; Microsoft's sample reads only six): not verified against an official MSI-based package.

## 2. Decoders and re-implementations: where they agree and differ

### Takeaway
All implementations agree on the outer layout, the `HMAC|IV|ciphertext` layout, ProfileVersion1/SHA256 and the `Detection.xml` element names. They differ on inner-ZIP compression, `ToolVersion` stamped, outer-entry order, in-memory vs streaming handling, and HMAC verification; none documents ZIP64 handling explicitly.

### Cited Findings
- Inner ZIP compression differs: ContentPrep `CreatePackage` uses `CompressionLevel.Fastest`; its `CreateUploadablePackage` (Graph path) uses `CompressionLevel.NoCompression`. — svrooij/ContentPrep `Packager.cs` @ `5468585`. IntuneAppBuilder uses `ZipFile.CreateFromDirectory(..., CompressionLevel.Optimal, false)`. — simeoncloud/IntuneAppBuilder `IntuneAppPackagingService.cs` @ `2144de7`. kenchan0130/intunewin uses `zip.Deflate` for files (default level). — kenchan0130/intunewin `internal/pack/pack.go` @ `2ecc219`
- Outer ZIP is Stored in all: ContentPrep `CompressionLevel.NoCompression, includeBaseDirectory: true`; IntuneAppBuilder `CompressionLevel.NoCompression` with comment "the portal can only read if no compression is used"; kenchan `Method: zip.Store`. Entry order differs: IntuneAppBuilder writes `Contents/IntunePackage.intunewin` then `Metadata/Detection.xml`; kenchan writes metadata first; ContentPrep follows `ZipFile.CreateFromDirectory` order. — files above
- ContentPrep warns: "On .net framework the zip file is created wrong, set this to true to use an alternative way" (backslash separators: "all files have directories set with the \ as seperator"); alternative method forces `/` and skips zero-length files (`if (file.Length > 0)`). — svrooij/ContentPrep `Zipper.cs`, `Packager.cs` @ `5468585`
- `ToolVersion` stamped: ContentPrep `"1.8.6.0"` (comment "Version of the latest IntuneWinAppUtil tool", stale vs 1.8.7); IntuneAppBuilder `"1.4.0.0"`; kenchan `"1.4.0.0"`; official sample seen with `1.8.4.0`. — files above; [svrooij post](https://svrooij.io/2023/10/04/analysing-win32-content-prep-tool/)
- XML namespaces: kenchan emits `xmlns:xsd`/`xmlns:xsi` attributes like the official output; IntuneAppBuilder builds the root with `XmlDocument` and writes `EncryptionInfo`/`MsiInfo` via `XmlSerializer` with empty namespaces, formatted with CRLF, no XML declaration; ContentPrep `OmitXmlDeclaration = true`, `Indent = true`. — files above
- Memory model: kenchan `io.ReadAll(zipReader)` and builds the output in a `bytes.Buffer` (whole package in RAM); ContentPrep `Unpack` decrypts into a `MemoryStream`; IntuneAppBuilder uses `FileOptions.DeleteOnClose` temp file streams. — files above
- HMAC verification: ContentPrep `DecryptStreamAsync` verifies ("Hashes do not match"); Kieselbach decoder does not. — files above
- ContentPrep doc comment "The output stream should be exactly 48 bytes larger than the input stream" is wrong by the 1-16 bytes of PKCS7 padding (the 63-byte measured difference in svrooij's own post shows it). — svrooij/ContentPrep `Packager.cs` @ `5468585`; [svrooij post](https://svrooij.io/2023/10/04/analysing-win32-content-prep-tool/)
- Python: no maintained Python packer found. GitHub repo search "intunewin language:python" returned only GUIs/wrappers and small repos (e.g. `emilkloeden/intunify` "Python scripts to generate very specific intunewin packages", last push 2022-11-08, 0 stars; `AlecDusheck/intunewin-mac` "Generate .intunewin on Mac. You probably shouldn't use this.", 0 stars). — `gh api search/repositories` output, 2026-10-26 (I did not read their source).

### Inferences
- Because Intune accepts packages from tools with different inner compression levels (IntuneAppBuilder has tenant integration tests; ContentPrep powers WinTuner per earlier findings), the inner compression level is very likely not validated; any valid ZIP the IME can extract should work. This is inference from adoption, not a test.
- Zero-length files are dropped by ContentPrep's alternative zip method; a native implementation should keep them (an installer may rely on an empty marker file).

### Gaps
- ZIP64: none of the community sources says how they handle >4 GiB; .NET `ZipArchive` and Go `archive/zip` are believed to write ZIP64 automatically, but I did not verify that against their docs in this session.
- I could not read the Go packer's crypto file in full (grep only), so its cipher mode is not independently confirmed here.
- svrooij's later posts "Decrypting intunewin files" and "Creating IntuneWin files with C#" were not read.

## 3. Does Intune validate beyond fileEncryptionInfo? Can Graph skip the outer ZIP?

### Takeaway
Yes, a Graph upload never sends the outer ZIP or `Detection.xml`: Microsoft's own sample extracts and uploads only the inner encrypted file, and IntuneAppBuilder and ContentPrep build the encrypted payload directly without ever writing the outer ZIP. `Detection.xml` is only the transport the admin-center upload reads; what the service validates on commit is not documented beyond "fully uploaded and validated".

### Cited Findings
- Microsoft sample flow: `Get-IntuneWinXML` extracts `detection.xml`; `Get-IntuneWinFile "$SourceFile" -fileName "$FileName"` extracts the inner encrypted file; `$Size = UnencryptedContentSize`; `$EncrySize = (Get-Item "$IntuneWinFile").Length`; `GetAppFileBody "$FileName" $Size $EncrySize $null`; `UploadFileToAzureStorage $file.azureStorageUri $IntuneWinFile $BlockSizeMB`; commit with the `fileEncryptionInfo` built from `Detection.xml` (lines 137-138, 229-263). — microsoft/mggraph-intune-samples `LOB_Application/Win32_Application_Add.ps1` @ `631eea2`
- IntuneAppBuilder `PublishAsync`: creates/gets the `win32LobApp`, creates a content version, posts `mobileAppContentFile` (`Size` = unencrypted ZIP length, `SizeEncrypted` = encrypted stream length), waits for `AzureStorageUriRequestSuccess`, stages blocks from `package.Data` (the encrypted stream), `CommitBlockListAsync`, posts `Commit` with `FileEncryptionInfo = package.EncryptionInfo`, waits for `CommitFileSuccess`, then patches `CommittedContentVersion`. The outer ZIP (`BuildPackageForPortalAsync`) is a separate method not used by publishing. — simeoncloud/IntuneAppBuilder `IntuneAppPublishingService.cs`, `IntuneAppPackagingService.cs` @ `2144de7`
- IntuneAppBuilder's own comment on `Detection.xml`: "This file is included in the zip file the portal expects. It is essentially a collection of metadata, used specifically by the portal javascript to patch data on the mobile app and its content (e.g. the Manifest of the content file)." — `IntuneAppPackagingService.cs` @ `2144de7` (community claim, not Microsoft)
- ContentPrep `CreateUploadablePackage`: "Encrypt a zip file to be uploaded to Intune programmatically, without zipping the result with the `MetaData\detections.xml` file", returning the `ApplicationInfo` (encryption info) for the commit call. — svrooij/ContentPrep `Packager.cs` @ `5468585`
- svrooij on the process: "the file you're uploading actually contains the data you need to decrypt it"; with wrong chunking "The upload would always succeed, but the commit step in the graph api would fail immediately with a commitFileFailed upload state." — [svrooij, Publish apps to Intune (2023-08-31)](https://svrooij.io/2023/08/31/publish-apps-to-intune/). Note: the post says "You then upload the initial .intunewin file to Intune", which conflicts with the Microsoft sample (inner file only); I treat the sample as authoritative.
- Graph `mobileAppContentFile.isCommitted`: "A committed app content file has been fully uploaded and validated by the Intune service." Properties include `size` ("original size"), `sizeEncrypted`, `manifest` ("manifest information, containing file metadata"), `isDependency`, `azureStorageUriExpirationDateTime`, and upload states including `commitFileFailed`. `sizeInBytes`/`sizeEncryptedInBytes` "To be deprecated in February 2025". (Updated 10/10/2025.) — [Graph mobileAppContentFile](https://learn.microsoft.com/en-us/graph/api/resources/intune-apps-mobileappcontentfile?view=graph-rest-1.0)
- The admin center path requires the container: "select a Windows installation file with the extension .intunewin. The app details appear." and "If you don't use the latest version, you'll see a warning that says the app was packaged using an older version of the tool." (Updated 04/14/2026.) — [add-win32](https://learn.microsoft.com/en-us/intune/app-management/deployment/add-win32)
- IntuneAppBuilder publishes to a real tenant in CI per the earlier findings (with the caveat that its scheduled tenant tests failed 2026-05-17/18 and the schedule was removed). — `plans/build-package/mdm-windows-tool-findings.md` 3.1 (not re-checked by me)

### Inferences
- A packer-less native pipeline needs: inner ZIP + ProfileVersion1 encryption + Graph calls (create `win32LobApp` with `fileName`, `setupFilePath`, install/uninstall commands, detection rules, `msiInformation` if MSI; content version; content file with `size`/`sizeEncrypted`; block upload; commit with `fileEncryptionInfo`; patch `committedContentVersion`). `Detection.xml` and `ToolVersion` disappear, so the portal's "older version of the tool" warning presumably cannot trigger (inference: the warning most likely reads `ToolVersion`; not verified).
- The plausible commit-time checks are HMAC over IV+ciphertext with `macKey`, decryption with `encryptionKey`/IV, `fileDigest` over the decrypted content, and size matches; this is consistent with every field being required, but Microsoft does not say which checks run.
- Graph path makes the MSI metadata a Graph property (`msiInformation`) instead of `MsiInfo` XML; on macOS/Linux MSI properties must be read by other means or supplied (ContentPrep and IntuneAppBuilder both read MSIs only on Windows: IntuneAppBuilder `GetMsiInfo` requires `OperatingSystem.IsWindows()`).

### Gaps
- No Microsoft statement on what commit validates, or on whether Detection.xml is read server-side or only by the portal's JavaScript.
- No first-hand test in this mission that a packer-less upload commits successfully; evidence is the Microsoft sample (which still starts from an official `.intunewin`) and community tools.
- I did not read the Graph `win32LobApp` resource page in this session (required fields unverified here).

## 4. Size and format limits

### Takeaway
Windows apps are capped at 30 GB; Azure block blobs allow up to 4,000 MiB per block and 50,000 blocks (so chunk size is a client choice; samples use 1, 4 and 25 MiB); payloads over 4 GiB need ZIP64 in both the inner and outer ZIP, which the official tool only got right from 1.8.4.

### Cited Findings
- "Windows application size is capped at 30 GB per app." — [add-win32](https://learn.microsoft.com/en-us/intune/app-management/deployment/add-win32) and [create-win32-package](https://learn.microsoft.com/en-us/intune/app-management/deployment/create-win32-package) (both updated 04/14/2026)
- Put Block: "The block must be less than or equal to 4,000 mebibytes (MiB) in size for version 2019-12-12 and later"; "A block blob can include a maximum of 50,000 committed blocks"; older service versions 100 MiB (2016-05-31 to 2019-07-07) and 4 MiB (earlier); "For a specified blob, all block IDs must be the same length" (else 400); block ID ≤ 64 bytes before base64; max 100,000 uncommitted blocks; uncommitted blobs are garbage-collected after a week. (Updated 01/20/2026.) — [Azure Put Block](https://learn.microsoft.com/en-us/rest/api/storageservices/put-block)
- Chunk sizes used: Microsoft Win32 sample `[UInt32]$BlockSizeMB = 1`, block ID = base64 of `chunk.ToString("0000")`, `x-ms-blob-type: BlockBlob`, then `comp=blocklist` XML (lines 262, 783-851) — mggraph-intune-samples `Win32_Application_Add.ps1` @ `631eea2`; Microsoft macOS sample `[UInt64]$BlockSizeMB = 4` and renews the SAS when `(Get-Date).ToUniversalTime() -ge $sasUriRenewTime` (lines 188, 334-336) — `macOS_Application_PKG_Add.ps1` @ `2e66845`; IntuneAppBuilder `chunkSize = 25 * 1024 * 1024`, renews the SAS URI after 450,000 ms, retries 307/403/400 up to 30 times — `IntuneAppPublishingService.cs` @ `2144de7`.
- Official tool history: "1.8.4 - Fixed an issue with version 1.8.3 where the Win32PrepTool will not work with files greater than 4gb." — microsoft/Microsoft-Win32-Content-Prep-Tool `ReleaseNotes.txt` @ `1d6cfcb`

### Inferences
- 30 GB with 1 MiB blocks = 30,720 blocks, under 50,000; 4-digit block IDs ("0000"-"9999") as in the Microsoft sample only reach 10,000 blocks, i.e. about 9.8 GiB at 1 MiB, so a native uploader should use larger blocks (e.g. 8-100 MiB) or wider fixed-length IDs. Arithmetic from the cited limits.
- The service-version block limit depends on the `x-ms-version` the client sends (or the SAS version); the Microsoft sample's header set was only partly read, so stay at ≤100 MiB blocks unless the version is pinned.
- ZIP64 is needed when the inner ZIP or any entry exceeds 4 GiB or entries exceed 65,535; the outer ZIP then also needs ZIP64 because it stores the >4 GiB inner file. Python's `zipfile` writes ZIP64 by default (`allowZip64=True`) per my prior knowledge, not re-read this session.
- HMAC-then-prepend requires a seekable output or a two-pass write (all implementations seek back to offset 0); a streaming bash pipeline must write ciphertext to a temp file first.

### Gaps
- Intune's SAS lifetime is not documented on the pages read (only `azureStorageUriExpirationDateTime` exists); community code renews at ~7.5 minutes.
- No source documents a per-file or per-block limit specific to Intune beyond the 30 GB cap.

## 5. Risks of a native build; Microsoft stance; licence; format changes across versions

### Takeaway
Technically low-risk (stable ProfileVersion1 since at least 1.4, four independent implementations agree), but unsupported: Microsoft says apps "must" be prepared with its tool and gives no container spec; the licence binds only use of Microsoft's software, and a native implementation built from Graph docs and MIT sample code does not use that software (not legal advice). The Graph path avoids most container risk.

### Cited Findings
- Microsoft stance: "Before you can add a Win32 app to Microsoft Intune, you must prepare the app by using the Microsoft Win32 Content Prep Tool." — [create-win32-package](https://learn.microsoft.com/en-us/intune/app-management/deployment/create-win32-package); "Be sure to use the latest version of the Microsoft Win32 Content Prep Tool. If you don't use the latest version, you'll see a warning..." — [add-win32](https://learn.microsoft.com/en-us/intune/app-management/deployment/add-win32)
- Format history in release notes (full file): 1.4 first release; 1.5 .msp fix; 1.6 catalog support for Win10 S; 1.7 Unicode file/folder names; 1.8/1.8.1 console fix + binaries; 1.8.2 `-v` and output redirection; 1.8.3 catalog-folder fix; 1.8.4 >4 GB fix; 1.8.5/1.8.6 crash fixes; 1.8.7 "Changed SHA256 to use FIPS-compliant algorithm", "Refactored logging to prevent crashes", "Added silent mode support", "Used compliant crypto algorithms". None announces a container or profile change. — microsoft/Microsoft-Win32-Content-Prep-Tool `ReleaseNotes.txt` @ `1d6cfcb`
- ProfileVersion1 is still the only profile: "Currently, only ProfileVersion1 is supported." — [Graph fileEncryptionInfo](https://learn.microsoft.com/en-us/graph/api/resources/intune-apps-fileencryptioninfo?view=graph-rest-1.0)

### Inferences
- Licence (not legal advice): the Microsoft terms govern "the software" (IntuneWinAppUtil.exe). Writing our own encoder from the Graph docs and the MIT samples involves no use, reverse engineering or redistribution of that software, so clauses 1/4 are not engaged. Two care points: (1) never derive our code from inspecting the official exe's output in a way that counts as reverse engineering it (observing its output files is generally not decompilation, but our basis should be the MIT sample + Graph docs); (2) do not copy GPL-3.0 ContentPrep code into aitools — read it as evidence only; Apache-2.0 IntuneAppBuilder and MIT Microsoft samples can be adapted with attribution.
- Risk register for a native build:
  - Undocumented container change (portal path only): low likelihood (no change since 1.4 in release notes), medium impact; avoided entirely on the Graph path.
  - ProfileVersion2 introduced and V1 retired: unknown likelihood, high impact; mitigate by monitoring the Graph `fileEncryptionInfo` page.
  - Support: Microsoft can decline support for apps not prepared with its tool ("must"); portal shows an older-version warning for stale `ToolVersion` stamps (stamping a current version string would be misrepresentation — avoid; prefer the Graph path).
  - Own crypto code: aitools would own key generation (must use a CSPRNG: Python `secrets`/`os.urandom` or `openssl rand`), HMAC ordering, PKCS7, and must keep keys out of logs (packages carry their own keys).
  - Tooling on macOS/Linux: Python stdlib has `hashlib`, `hmac`, `zipfile`, `secrets`, `base64`, `xml.etree` but no AES; AES needs the `openssl` CLI (`openssl enc -aes-256-cbc -K <hex> -iv <hex>`, PKCS7 by default; earlier findings verified LibreSSL 3.3.6 on the Mac) or a third-party package (`cryptography`, would need `/tool-eval`). A pure-bash path is `zip`/`python3 -m zipfile` + `openssl enc` + `openssl dgst -sha256 -mac HMAC -macopt hexkey:` over `IV||ciphertext`, then prepend the MAC.
  - Upload fragility: community reports SAS 403s and commit failures ("the Intune APIs are fundamentally unstable and sometimes 403s will be encountered randomly", IntuneAppBuilder comment) — needs retries, renewUpload, and state polling with timeouts.
- What a native implementation needs (minimal): (1) ZIP the source folder (ZIP64-capable, `/` separators, keep empty files); (2) SHA-256 of that ZIP = `fileDigest`; (3) random 32-byte key, 32-byte MAC key, 16-byte IV; (4) AES-256-CBC/PKCS7 encrypt; (5) HMAC-SHA256(macKey, IV||ciphertext) = `mac`; (6) write `mac|IV|ciphertext`; then either (7a) Graph upload with `size` = ZIP length, `sizeEncrypted` = output length, commit `fileEncryptionInfo`, or (7b) for portal use, wrap in a Stored outer ZIP with `IntuneWinPackage/Contents/IntunePackage.intunewin` and a `Detection.xml` following the schema in section 1. Validate by round-trip decrypt (ContentPrep-style HMAC check) and one tenant acceptance test.
