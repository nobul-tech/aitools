# Dispatch Windows builds now, go native later

**v1.0** — Mission MDM-WINTOOL-DR (coordinator S3-MdmWinToolDR, commander Jose), 2026-10-26. Synthesised from five research notes (Official, Format, Community, Fallbacks, Ecosystem) in `S3-MdmWinToolDR/research_notes/Intunewin packaging without Windows/`, re-checked against the earlier `plans/build-package/mdm-windows-tool-findings.md` (v1.0) and `S3-MdmWinTool/` notes. Every web source was read on **2026-10-26** unless marked otherwise; code is cited as repo/path@commit.

Microsoft's only `.intunewin` packer, `IntuneWinAppUtil.exe` v1.8.7, is a Windows-only .NET Framework 4.7.2 tool with no macOS, Linux or .NET (Core) build and no roadmap for one, and its licence blocks the obvious shortcuts: redistribution (4e), reverse engineering (4b) and arguably working around its limits (4a). The format itself is not Windows-bound. It is a Stored ZIP holding an AES-256-CBC/PKCS7 + HMAC-SHA256 payload ("ProfileVersion1") and a cleartext `Detection.xml`, and at least four independent implementations agree on it byte for byte, so it can be built on any host. More than fifteen community packers do exactly this, but none is official, the two with real adoption (simeoncloud/IntuneAppBuilder, svrooij/ContentPrep) carry yellow flags, and Intune has rejected community-packed output without warning at least once (IntuneAppBuilder #53, 2025-08). **No cross-platform option is fit to adopt today without a `/tool-eval` and a tenant acceptance test.** The recommended path for build-package is to keep the official tool on a Windows host: a GitHub-hosted `windows-2022` runner, which costs $0 because nobul-tech/aitools is public. Every non-Windows host (macOS, Ubuntu, Claude Code web, Cursor cloud) reaches that runner through `gh workflow run` / `gh run download`. The way to real local builds on all platforms is a small native ProfileVersion1 encoder in aitools, built from Microsoft's Graph docs and MIT sample code with python3 + openssl (pwsh/.NET on Windows). It goes through `/tool-eval` and `/tool-adopt` (for openssl and its delivery on each platform) and a tenant test. IntuneAppBuilder is the existing-tool alternative to send through the same gate.

## Scope, assumptions and recorded conflicts

The question is what can build Intune Win32 packages on macOS, Linux and Windows, so that build-package can make its Windows Intune app, macOS PKG and Linux `.deb` from macOS, Windows, Ubuntu, Claude Code web and Cursor cloud hosts. The report also asks whether any option is fit to adopt. Every route was covered: official tools and APIs, community packers, a native container implementation, Graph upload without the outer container, the official tool under Wine/Mono/.NET, hosted Windows CI, and ecosystem practice.

The assumptions are stated here because no follow-up questions were asked. This was a background run. "All platforms" means the build host may be macOS, Windows, Ubuntu, Claude Code web or Cursor cloud. nobul-tech/aitools is a public repository (`gh repo view`, per the Fallbacks notes). ## Microsoft ships one Windows tool and has said nothing in 6.5 years

The current tool is **v1.8.7, released 2025-08-13**. The README lists one prerequisite, **".NET Framework 4.7.2"**, and names no OS or CPU architecture ([README](https://github.com/microsoft/Microsoft-Win32-Content-Prep-Tool)). The repo has 1,556 stars and 298 forks, was last pushed 2026-08-24, and its releases carry no uploaded assets (`gh api repos/microsoft/Microsoft-Win32-Content-Prep-Tool`). The x64/PE32+ binary facts come from the earlier mission's binary parse and were not re-verified in this pass, which downloaded nothing. The Linux request, **issue #26 "Linux executable?", has been open since 2020-02-04 with no Microsoft reply**. A Microsoft engineer (ameltzer-MSFT) closed the Cloud Shell request #86 with the single comment "#26" ([issue #26](https://github.com/microsoft/Microsoft-Win32-Content-Prep-Tool/issues/26)). Intune's What's New page (last updated 10/12/2026) has zero mentions of "Content Prep", "intunewin" or "IntuneWinAppUtil" ([What's new in Intune](https://learn.microsoft.com/en-us/intune/whats-new/)). Microsoft Learn states the requirement as a "must": "Before you can add a Win32 app to Microsoft Intune, you must prepare the app by using the Microsoft Win32 Content Prep Tool." The admin-center Win32 flow accepts only a file "with the extension .intunewin" and warns when a package was built with an older tool version ([create-win32-package](https://learn.microsoft.com/en-us/intune/app-management/deployment/create-win32-package); [add-win32](https://learn.microsoft.com/en-us/intune/app-management/deployment/add-win32), both updated 04/14/2026). Apps are capped at **30 GB** ([add-win32](https://learn.microsoft.com/en-us/intune/app-management/deployment/add-win32)).

The licence PDF was read in full by two researchers, at commit `1d6cfcbdf8c28edc596337031f74df951f38f718`. It allows "any number of copies" (clause 1). It forbids "work around any technical limitations" (4a), "reverse engineer, decompile or disassemble" (4b), and "share, publish, rent, or lend the software, or provide the software as a stand-alone hosted offering for others to use" (4e). Clause 3 lets the software "collect information about you ... and send that to Microsoft". No clause mentions an operating system, emulation, containers, CI, or re-implementing the file format ([Licence PDF](https://github.com/microsoft/Microsoft-Win32-Content-Prep-Tool/blob/1d6cfcbdf8c28edc596337031f74df951f38f718/Microsoft%20License%20Terms%20For%20Win32%20Content%20Prep%20Tool.pdf)). The licence governs "the software", so an independently written encoder does not engage it. Running the exe and redistributing it are what it restricts.

Microsoft offers alternatives that avoid `.intunewin`, but none fits a custom installer payload as build-package is designed. The **Enterprise App Catalog** holds only prepackaged apps that Microsoft prepared, and it is a paid Intune Suite feature ([Enterprise App Catalog](https://learn.microsoft.com/en-us/intune/app-management/deployment/add-enterprise-catalog-app)). The **Microsoft Store app (new)** type deploys only apps found by searching the Store ([Add Microsoft Store apps](https://learn.microsoft.com/en-us/intune/app-management/deployment/add-microsoft-store)). **Windows LOB** takes `.msi`/`.msix`/`.appx` directly, with no `.intunewin`, but "Only one command-line argument can be specified" ([Add a Windows LOB app](https://learn.microsoft.com/en-us/intune/app-management/deployment/add-lob-windows)). **Platform PowerShell scripts** must be "less than 200 KB" and carry no payload ([run-powershell-scripts-windows](https://learn.microsoft.com/en-us/intune/device-management/tools/run-powershell-scripts-windows)). Wrapping the payload as an MSI or MSIX built on a non-Windows host would change build-package's deliverable. The tooling for that was not researched (unknown).

## The format is simple, stable and only half documented by Microsoft

A `.intunewin` is an **unencrypted, Stored ZIP** with two entries. `IntuneWinPackage/Contents/IntunePackage.intunewin` is a ZIP of the source folder, encrypted as `HMAC-SHA256[32] | IV[16] | AES-256-CBC/PKCS7 ciphertext`. `IntuneWinPackage/Metadata/Detection.xml` holds, in cleartext and base64, the `EncryptionKey`, `MacKey`, `InitializationVector`, `Mac`, `ProfileIdentifier` (`ProfileVersion1`), `FileDigest` (SHA-256 of the unencrypted inner ZIP) and `FileDigestAlgorithm` (`SHA256`), plus `Name`, `UnencryptedContentSize`, `FileName`, `SetupFile` and a `ToolVersion` attribute ([svrooij, Analysing Win32 Content Prep Tool, 2023-10-04](https://svrooij.io/2023/10/04/analysing-win32-content-prep-tool/); svrooij/ContentPrep `src/SvR.ContentPrep/Encryptor.cs`, `Models/ApplicationInfo.cs` @ `54685857f7ee450fe106591e8dc315b578311b84`). The cipher mode is pinned by an arithmetic check against the official tool's own output. The inner plaintext was 5,957,009 bytes. PKCS7 adds 15 bytes, and the HMAC and IV add 48, giving **exactly the 5,957,072 bytes measured**. This rules out the AES-CTR claim in maxihafer/content-prep's README. A package carries its own decryption keys, so built packages are confidential until uploaded.

Microsoft documents only part of this. Graph's `fileEncryptionInfo` fixes the sizes: a 16-byte IV, a 32-byte `mac` ("The hash of the concatenation of the IV and encrypted file content"), a 32-byte `macKey`, "only ProfileVersion1", and SHA256 for the digest "prior to encryption". It never names AES, CBC, PKCS7, HMAC or the key length ([fileEncryptionInfo](https://learn.microsoft.com/en-us/graph/api/resources/intune-apps-fileencryptioninfo?view=graph-rest-1.0), updated 09/13/2024). The algorithm is official only as **MIT sample code**. `macOS_Application_PKG_Add.ps1` (@ `2e668455288ebc43b7356b2d9b0c537e24c409f4`) and the 2026-06 `MSIX_Application_Add.ps1` write the HMAC|IV|ciphertext layout with .NET `Aes` and `HMACSHA256`. The MSIX readme says in prose that it "Encrypts a copy of the package (AES + HMAC-SHA256)" and that a Win32 `.intunewin` is "pre-encrypted" and contains `detection.xml` ([mggraph-intune-samples LOB readme](https://github.com/microsoft/mggraph-intune-samples/blob/main/LOB_Application/readme.md)). The Graph commit page's pointer to the ProfileVersion1 sample, `https://aka.ms/fileencryptioninfo`, **now redirects to Bing** (`curl -sI`, 2026-10-26; [commit action](https://learn.microsoft.com/en-us/graph/api/intune-apps-mobileappcontentfile-commit?view=graph-rest-1.0)). The container, the inner ZIP and the `Detection.xml` schema are documented only by the community. Microsoft's own Win32 sample confirms them implicitly by parsing those exact element names ([Win32_Application_Add.ps1](https://github.com/microsoft/mggraph-intune-samples/blob/main/LOB_Application/Win32_Application_Add.ps1) @ `631eea28ae4be8265b89727ffa9b9e90f94a15c2`).

**Graph upload never sends the outer container.** Microsoft's Win32 sample extracts `Detection.xml` for the keys and then uploads only the inner encrypted file to the Azure Storage SAS URI. It commits the `fileEncryptionInfo` built from that XML, with `size` = `UnencryptedContentSize` and `sizeEncrypted` = the inner file's length (`Win32_Application_Add.ps1` lines 137-138, 229-263 @ `631eea2`). IntuneAppBuilder publishes the same way, without ever writing the outer ZIP (`Source/IntuneAppBuilder/Services/IntuneAppPublishingService.cs` @ `2144de74a20ab3a76382befb16c375b42925899c`). ContentPrep has a dedicated `CreateUploadablePackage` for this path (`Packager.cs` @ `5468585`). MSEndpointMgr's 2026-08 walkthrough says the same thing: "Every step is a Graph call except the upload, which goes straight to Azure Blob Storage" ([msendpointmgr.com, 2026-08-16](https://msendpointmgr.com/2026/08/16/win32-app-intune-powershell-graph/), partial read). A packer-less Graph pipeline therefore needs only Microsoft-sourced pieces. What the service validates at commit is not documented beyond "fully uploaded and validated by the Intune service" ([mobileAppContentFile](https://learn.microsoft.com/en-us/graph/api/resources/intune-apps-mobileappcontentfile?view=graph-rest-1.0)). Whether a Win32 content file that the tool did not produce commits successfully is **untested by this mission**. The evidence is community tools only. The release notes show no container or profile change from 1.4 to 1.8.7, and 1.8.4 fixed >4 GB files (`ReleaseNotes.txt` @ `1d6cfcb`). Azure Put Block allows up to 4,000 MiB per block and 50,000 blocks ([Put Block](https://learn.microsoft.com/en-us/rest/api/storageservices/put-block)). Microsoft's sample uses 1 MiB blocks with 4-digit IDs, which reaches only about 9.8 GiB, so a native uploader needs larger blocks or wider IDs.

The implementations differ in ways that matter for anyone building one. They choose different inner compression levels (Fastest, Optimal, Deflate, None) and stamp different `ToolVersion` values: ContentPrep "1.8.6.0", IntuneAppBuilder and kenchan "1.4.0.0", iancohn "1.8.7.0". Not every one verifies the HMAC on decode. ContentPrep's alternative zipper drops zero-length files. One documented failure mode: an outer ZIP written with .NET Framework's `NoCompression`, which still emits Deflate blocks, made Intune report **"Your app is not ready yet"** ([ThomasHoins/New-IntuneWin](https://github.com/ThomasHoins/New-IntuneWin)). The portal's "older version of the tool" warning most likely keys off `ToolVersion` (inference, unverified). That creates a dilemma for any non-official portal package: stamping an old version invites the warning, and stamping the current one misrepresents the tool. The Graph path sidesteps it, because no `Detection.xml` is sent.

Against the ranked principles, the official exe wins principles 1 and 2 outright and loses 4 and 5, because it has no non-Windows delivery. ## The ecosystem defaults to Windows runners and fetches the exe at run time

Every published Win32 CI pipeline found runs on `windows-latest` with the official exe. Examples are aaronparker's PSPackageFactory with IntuneWin32App ([import-package.yml](https://github.com/aaronparker/packagefactory/blob/main/.github/workflows/import-package.yml)) and IntuneAppBuilder's own CI ([ci.yml](https://github.com/simeoncloud/IntuneAppBuilder/blob/master/.github/workflows/ci.yml)). No Microsoft-published GitHub Action or Azure DevOps task that builds `.intunewin` was found, and no published Linux or macOS CI template using a native packer was found either. A search cannot prove absence. The most-downloaded community module, **MSEndpointMgr/IntuneWin32App (961,872 PSGallery downloads)**, does not pack natively. `New-IntuneWin32AppPackage` downloads `IntuneWinAppUtil.exe` from the moving `raw/master` URL into `$env:TEMP`, with no hash check, and runs it ([New-IntuneWin32AppPackage.ps1](https://github.com/MSEndpointMgr/IntuneWin32App/blob/master/Public/New-IntuneWin32AppPackage.ps1); [PSGallery](https://www.powershellgallery.com/packages/IntuneWin32App)). PSAppDeployToolkit's official guide lists the Microsoft tool as a prerequisite ([PSADT deploy-with-intune](https://psappdeploytoolkit.com/docs/how-to/deploy-with-intune)). Several projects that look like cross-platform packers wrap the Microsoft exe and are Windows-only: notapkgtool ("creating .intunewin packages requires Windows"), IntuneGet (a "Windows runner for .intunewin file generation"), and the clstrickland composite action ([notapkgtool](https://github.com/RogerCibrian/notapkgtool); [IntuneGet](https://github.com/ugurkocde/IntuneGet)). The SaaS vendors (Patch My PC Cloud, Robopack) build packages server-side and do not say which packer or OS they use. Patch My PC Publisher runs on Windows ([Patch My PC requirements](https://docs.patchmypc.com/patch-my-pc-publisher/requirements/intune-requirements/software), partial; [Robopack Custom Packaging](https://docs.robopack.com/docs/features/custom-packaging/), partial).

Non-Microsoft packing still reaches tenants at scale. **WinTuner packs with ContentPrep by default** and allows the Microsoft exe only behind an environment variable that it refuses on non-Windows ([WingetServiceCollectionExtension.cs](https://github.com/svrooij/WinTuner/blob/main/src/WingetIntune/WingetServiceCollectionExtension.cs)). The Mac-admin AutoPkg processors in almenscorner/intune-uploader implement ProfileVersion1 in Python (`os.urandom` keys, AES-CBC, PKCS7, HMAC-SHA256 over IV+ciphertext), but only for macOS app types ([IntuneUploaderBase.py](https://github.com/almenscorner/intune-uploader/blob/main/IntuneUploader/IntuneUploaderLib/IntuneUploaderBase.py) lines 344-407). That is the closest precedent for a python-plus-crypto native encoder, and it shows Intune accepts non-.NET ProfileVersion1 content for at least one app family. Acceptance holds in practice but is not guaranteed. IntuneAppBuilder #53 shows that a backend enforcement change can turn community output into "File format is not recognized" / `commitFileFailed` for weeks without any change to the tool ([#53](https://github.com/simeoncloud/IntuneAppBuilder/issues/53)).

On cost and reach, GitHub Actions is free for public repositories on standard runners, and Windows 2-core x64 costs $0.010 per minute on private ones ([Actions billing](https://docs.github.com/en/billing/concepts/product-billing/github-actions); [runner pricing](https://docs.github.com/en/billing/reference/actions-runner-pricing)). `windows-2019` was retired by 2025-06-30, and **no windows-2022 deprecation is announced** ([runner-images #12045](https://github.com/actions/runner-images/issues/12045); [runner-images](https://github.com/actions/runner-images)). The runner-images policy allows only MIT, Apache or GNU licences for preinstalled tools, so the exe will never come preinstalled and must be fetched per job. `workflow_dispatch` triggers only for a workflow file that "exists on the default branch" ([Events that trigger workflows](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows)). Claude Code web VMs are "Ubuntu 24.04 on x86_64". Their GitHub proxy serves REST calls for attached repositories and rejects GraphQL ([Claude Code cloud environments](https://code.claude.com/docs/en/cloud-environments.md)). Whether that proxy's scoped credential can POST a workflow dispatch, and whether artifact download redirects pass it, is **unknown**. Cursor cloud agents have internet access by default, and their `gh` calls come from Cursor's egress ranges, but nothing documents `gh` authentication for Actions ([Cursor Secrets & Network](https://cursor.com/docs/cloud-agent/security-network)).

The commander's condition was that "if it finds that it only runs on windows" an alternative must be found. The finding is that the *official tool* runs only on Windows, while the *format* runs anywhere. Ranks 1-2 make build-package usable from every host today, without leaving Microsoft's supported path. Rank 3 is the alternative that makes the Windows package buildable on every host. Its gate is the commander's call on owning the crypto, plus the `/tool-eval` and `/tool-adopt` the commander asked for. MSI/MSIX LOB and platform-script bootstrappers would change the deliverable, and the non-Windows MSI/MSIX tooling was not researched (unknown).

## Conclusion

The question was never "can a non-Windows host write a `.intunewin`". Four independent codebases and Microsoft's own MIT samples settle that it can. The real question is whose word stands behind the bytes. Today only Microsoft's tool has the official "must", and only on Windows. Every alternative trades that endorsement for reach, and the 2025 IntuneAppBuilder outage shows the trade is a live operational risk, not a theoretical one. The decisive asymmetry is the Graph path. Once aitools uploads through Graph, the undocumented container, the `Detection.xml` schema and the `ToolVersion` dilemma drop out, and every remaining byte rests on a Microsoft source. That makes a native encoder a smaller, better-sourced commitment than adopting any third-party packer. The gaps are its acceptance in a real tenant and the commander's willingness to own about 200 lines of crypto.

The practical consequence for build-package is a two-step plan, not a choice. Ship ranks 1-2 now, so every host can request a Windows package through the official tool. Then decide rank 3 against IntuneAppBuilder, and run a scheduled tenant acceptance test whichever wins, because Intune's commit-time checks are undocumented and have changed without notice before. The unknowns to retire first are cheap: whether the Claude Code web GitHub proxy allows workflow dispatch and artifact download, whether openssl is present on the target Ubuntu images, and whether a self-encrypted Win32 content file commits in a real tenant.
