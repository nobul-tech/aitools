# S3-MdmWinTool-Critic verdict on `plans/build-package/mdm-windows-tool-findings.md` v1.0 (v1.0)

Reviewer: S3-MdmWinTool-Critic (independent; did not read the Eval, Research or Probe notes or `.scratch/session-mdmw-*/` other than my own `session-mdmw-crt/`). All sources read 2026-10-26 with `gh api` (GitHub, raw file contents), `curl` of the NuGet search JSON, the licence PDF (fetched as a document at commit `1d6cfcb`, read with Read), and Microsoft Learn pages with chrome-devtools (own tab, innerText). WebSearch used for discovery only. No binary downloaded or run.

## Verdict

**UPHELD WITH CORRECTIONS.**

1. The recommendation is correct: Microsoft's tool is the only official packer, and it runs on Windows only. Building on the GitHub `windows-2022` runner with the official exe, with macOS and Linux reporting `n/a`, is the right answer under the ranked principles.
2. Microsoft's own docs back it more strongly than the report says. Learn says "you **must** prepare the app by using the Microsoft Win32 Content Prep Tool", and the admin center warns on packages built with an older tool version. The report's correction of design.md 3(a), which calls that sentence "wrong as a statement of fact", overstates its case and should be reworded.
3. The licence quotes (clauses 1, 3, 4(a)-(e)), the release dates, the commit-signing facts, the runner .NET Framework line and the Graph `fileEncryptionInfo` quotes are all correct.
4. Activity is understated. A Microsoft org MEMBER (`brmcmill`) was answering issues on 2026-10-08, and that MEMBER endorsed the raw.githubusercontent URL as the "good" download. There was also a commit on the `test` branch on 2026-08-24. The yellow flag stands, but its reasons need updating.
5. #167 has 0 comments, is an unconfirmed single report and has no Microsoft reply, so it is not a confirmed regression. A recurring console-buffer crash class (#138, #165) is a CI risk the report does not name. The Enterprise App Catalog does not remove the need to package (it is a curated catalog and a paid add-on).

## Claims checked and found correct

- **Releases** (`gh api repos/microsoft/Microsoft-Win32-Content-Prep-Tool/releases`): v1.8.7 published 2025-08-13T21:30:41Z, v1.8.6 2024-02-28T03:40:11Z. Every release has 0 assets. 14.5 months to 2026-10-26 is correct. No release since.
- **Commit signing** (`gh api .../commits`): 35a412b (2025-07-31) and 99dbe4b (2025-08-13) are `unsigned`. The merge commits 1d6cfcb, 06a8597 and cbc12f0 are `valid`. `commits?path=IntuneWinAppUtil.exe` confirms that 99dbe4b and 35a412b are the last two exe changes.
- **Repo contents** (`gh api .../contents`): `IntuneWinAppUtil.exe` size 62520, blob `566b5e0371a82ef5bd4e59f4314d72f0996d57f3` (matches 2.4). Also the licence PDF, README.md, ReleaseNotes.txt and SECURITY.md, and no source code (matches 2.1).
- **Licence PDF at `1d6cfcb`**, read in full: clause 1 "You may install and use any number of copies of the software."; clause 3 "The software may collect information about you and your use of the software and send that to Microsoft."; clause 4 "you will not (and have no right to): a) work around any technical limitations in the software; b) reverse engineer, decompile or disassemble the software ...; c) remove, minimize, block, or modify any notices ...; e) share, publish, rent, or lend the software, or provide the software as a stand-alone hosted offering for others to use." All verbatim as quoted in 2.5. Preamble: "BY USING THE SOFTWARE, YOU ACCEPT THESE TERMS." Consistent with Q1. A 2020 commenter in #26 read 4(e) the same way for a hosted packager.
- **README**: ".NET Framework 4.7.2" prerequisite; "By downloading and using Microsoft Win32 Content Prep Tool, you agree to such license terms."; flags `-c -s -o -a -q -qq -v -h`; `-v` "Only available starting version 1.8.2". "The generated .intunewin file contains all compressed and encrypted source setup files and the encryption information to decrypt it". - **Principle ranking**: principle 1 (official endorsement) decides it. Microsoft documents only its own tool, says "must", and warns on older tool versions. Every alternative is unofficial, and the best one (IntuneAppBuilder) has unverified NuGet provenance (principle 2). A cheaper design via a native Graph upload would drop principle 1 for principle 4 and would still produce no portal-uploadable `.intunewin` from Microsoft-documented parts (3.2). The windows-2022 runner costs nothing to own. I found no better design.
