## Summary

1. `setup-user-cursor.sh/.ps1` step 4 reads `~/.aitools/rules/.aitools-rules-manifest`. It fans out only names whose source is `shared` or `dotprofile` (case-insensitive), and skips `*.bak.*` and the manifest silently.
2. For each `aitools` or `retired` name, it backs up and removes `~/.cursor/rules/<stem>.mdc`, but only when the fan-out created it. Recognition:
   - the new aitools-fanout marker, which is the line after the frontmatter: `<!-- aitools-fanout: generated by setup-user-cursor from ~/.aitools/rules/<name>; edit that rule, not this file -->`;
   - or, for #87-era files without a marker, content equal to the conversion of the harness copy or of one of its `*.bak.*` backups.
   Any other file of that name is kept, with a WARN and an ACTION row listing it, because Cursor still loads it.
3. With no manifest or a bad header, nothing is fanned out and nothing is removed. The step writes a WARN row (`no rules manifest` / `rules manifest not v1`) and the ACTION "Run aitools to rebuild ~/.aitools/rules and its manifest". Invalid lines are ignored with a warning.

## Decisions taken

- **Recognition** is the marker plus a legacy content match. The match is cited in `cursor_rule_is_fanout` / `Test-CursorFanoutRule`, and in the prune block of both scripts.
- **Limitation:** a #87-era `.mdc` whose matching harness copy and backups are all gone (backup_file keeps 20) cannot be recognised. It is kept, with a WARN and an ACTION row.
- **Dev-path wiring:** the reviewer noted that on this branch `scripts/aitools` and `aitools-install.sh` do not run deploy-harness. PR #106 (S3-H2-Hookin) wires it in. Until #106 merges, a dev run reports WARN `no rules manifest` and changes nothing, which is the safe behaviour.
- **Safe behaviour without a manifest:** do nothing, with WARN and ACTION. This is what the launch prompt suggested.
- **Missing user-level source file:** a warning, not an error.
- **Summary row:** when rules were fanned out, removals appear as `DETAIL|cursor rules|removed: <f>` rows plus the log count. The tracker has no `removed` outcome, and aitools-lib is out of scope.
- **PS1 backups:** a name with `[ ] * ?` is backed up with `Copy-Item -LiteralPath` instead of Backup-File.

## INCIDENT markers (not filed)

1. INCIDENT: `Backup-File` in `scripts/aitools-lib.ps1:781-805` uses `Test-Path $FilePath` and `Copy-Item -Path`, both of which treat the path as a wildcard. A name containing `[ ]` gets no backup, yet `$script:BackupFileOk` stays `$true`, so callers (`Deploy-ManagedFile`, setup-user-cursor before this PR) write or remove without a backup. Fix: switch to `-LiteralPath` in the library.
2. INCIDENT (low): the deploy tracker (`deploy_tracker_record` / `Record-DeployOutcome`) has no `removed` outcome, so a pruning consumer cannot put removals into its main row text.

## Reviewer verdict

- **First review: NO BLOCKING FINDINGS**, with 4 findings: https://github.com/nobul-tech/aitools/pull/110#pullrequestreview-5623312379 (`S3-H2-Cursor-Review-verdict.md`). All 4 are fixed in 7f7fc5c:
  1. (medium) A #87 copy of a rule edited or retired since that run stayed loaded, with only an info log. Fix: the content check now also tries the harness copy's `*.bak.*` backups. A file still unrecognised gets a WARN and an ACTION row that lists it.
