## The design: one schema, three documents (schema v1, proposed)

**One schema.** Every node and every item type is defined once. Wherever a node name appears, it means the same thing. Each document uses the nodes it needs:
- The **mission brief** is what is supposed to happen. The delegating agent writes it before launch, and it is the delegation prompt.
- The **AAR** is what happened against that brief. The delegate writes it at the end.
- The **running estimate** is the session's living record. Every agent writes to it continuously.

The doctrine read by mission 874d-1-aar-doctrine gives the same split:
- the AAR opens with the "Review of objectives and intent", then "what happened", why, and sustain/improve (TC 7-0.1, 2025, 3-2);
- the running estimate holds the facts and assumptions beside the restated mission and is updated as they change (FM 5-0, 2024, table C-1, C-7);
- the brief is the order plus its reporting requirements (ADP 6-0, 2026, 2-77: a CCIR "establishes a reporting requirement").

**Blockers in the brief:** none. Reporting a blocker at once is a standing duty of every delegate (D-DEL9, D-SR26), written in the delegation rule and `/delegate`, not in each brief. A blocker the delegating agent already knows about at launch is a fact or a constraint in the brief, and the objective it affects says so.

**Where the facts come from** (proposed text for `/delegate`; the skill has no guidance on facts today). The delegating agent fills `facts[]` from three sources only:
1. **Its running estimate.** It copies the facts that bear on the mission, each with its id and evidence.
2. **State it verified just before launch.** For example `git fetch` and the log, the file as it is on disk, `gh pr view` or the CI status, a test run. The command or `file:line` is the evidence. This is the existing `/delegate` step "Verify state before launching".
3. **The commander's words,** quoted with the session and line.

Anything it has not verified is an assumption, never a fact. Doctrine: "an assumption mislabeled as a fact may prove more dangerous" (FM 5-0, 2024, 5-43).


- `WRITE_BLOCKED` becomes a deviation (cause `blocker`, from a `rule`), already reported at once;
- a `CONFLICT:` line becomes an ambiguity resolved by D-DEL6;
- an `INCIDENT:` marker becomes an observation with `incident: true`;
- PR URLs and files become an objective's `deliverables` (RFI 874d-17).

**Blockers in the AAR:**
- the objective's status is `partly` or `not accomplished`;
- a deviation explains it (`cause: blocker`, `from` the objective);
- an assumption is marked falsified, if a wrong assumption was the cause;
- a proposal or RFI, if only the commander can clear it.

### Running estimate

One per session (D-SR8). Written by the session commander and every delegate. Not shared across sessions (D-SR9).

```
provenance
  document           running-estimate
  schema_version, version
  session_id
  maintainer         the session commander
  created_at, updated_at
intent               the commander's intent for the session; main_effort
assessment           is the session proceeding according to the commander's intent?
                     updated every turn (FM 1-02.1 "running estimate"; FM 5-0 table C-1 item 6)
objectives[]         the session's objectives: the commander's orders verbatim + transcript
                     line + status + how + refs
missions[]           the delegation log: mission, agent_id, parent, status
                     (launched | running | returned | failed), brief_ref, aar_ref
facts[], assumptions[], decisions[], ambiguities[]
deviations[], observations[]
operational_learning[]
proposals[]
rfis[]
```

Every item carries `agent_id` and `agent_type`, so the estimate is the union of what every agent wrote. The AAR of mission M is the set of items its delegate wrote (`mission` = M). The brief is a file whose path is in `missions`.

### Store (proposed, RFI 874d-4)

```
session DB    .aitools/sessions/<first 10 characters of the session id>.db (e.g. dbd05b0c-2.db):
              one per top-level session (exists; gitignored). The session agent and all
              of its delegates, at every level, write to this one DB.
              WAL, busy_timeout 5000, BEGIN IMMEDIATE (scripts/harness-db.py): parallel
              writers wait their turn; nothing is lost
items         one row per item, every type, every agent (no table per agent)
                id, type, text, status, severity, fields (JSON: the type's own fields),
                agent_id, agent_type, mission,
                source_kind, source, quote, created_at, updated_at, version
              no session_id column: the DB file is the session; the export adds it
refs          from_id, to_id, kind (objective | deviation | observation | deliverable |
              validated | invalidated)
missions      one row per delegate: mission (name), agent_id, parent (the delegating
              delegate's mission name; empty when the session agent delegated),
              brief_path, aar_path, status (launched | running | returned | failed)
views         the AAR of mission M = the items with mission = M, rendered in the AAR
              schema (harness-db.py aar --mission M); the estimate = all items
export        a per-session JSON estimate in the schema above, committed at session end
              (the session DB is gitignored, so only the export carries forward)
```

**Do we still need `attributed_to` and `session_id`?**
- **`attributed_to`: no.** It is replaced by `agent_id`, which holds who wrote the row (D-SR25). Who *said* it is `source.kind` + `quote`. For example, when the session agent records one of the commander's decisions, `agent_id` is the session id, `source.kind` is `commander` and the quote is his words.
- **`session_id`: not as a column.** It cannot tell the session agent from its delegates, because every row in the DB has the same session. The DB file is the session, and the export adds the session id.

**How each agent writes** (D-SR25):

| Writer | `--session` | Identifies itself with | `agent_id` stored | `agent_type` |
|---|---|---|---|---|
| Session agent (the top-level Claude Code session) | its own session id | nothing more | its session id | `session` |
| Delegate, at any level | the top-level session's id, given in its brief (`provenance.session_id`); never its own subagent id | `--mission <its mission name>` | its subagent agentId, looked up by harness-db in `missions` | `delegate` |
| Hook | the session id from its input | `--agent <hook name>` | the hook name | `hook` |
| The commander (command channel) | the session id | | `commander` | `commander` |

The delegating agent, whether the session agent or a delegate, registers each mission:

```
before launch    harness-db.py mission start --session <top session id> --mission <name>
                   --parent <its own mission name; the session agent omits it>
                   --brief <brief path>
agentId known    harness-db.py mission update --session <top session id> --mission <name>
                   --agent-id <agentId>
                   (a background launch returns the agentId at once; a foreground
                   launch returns it when the delegate finishes)
hand-back        harness-db.py mission end --session <top session id> --mission <name>
                   --status returned|failed --aar <path>
```

Once the agentId is registered, harness-db writes it on every row of that mission, including rows written before it was known. Rows by any agent can then be queried directly: `SELECT * FROM items WHERE agent_id = ?`.

**Why `--mission`.** A running delegate knows its mission name for certain: the name is in its prompt (D-DEL1, `/delegate` naming). It does not know its agentId:
- Claude Code assigns the agentId at launch and returns it to the delegating agent, not to the delegate.
- The file that links name and agentId is `subagents/agent-<agentId>.meta.json`, whose `description` starts with the name. For delegate 874d-1-aar-doctrine it was created at 20:55:18Z, when the delegate finished, about 11 minutes after it started (its output directory dates from 20:44Z). So a running delegate cannot rely on it.

The session agent passes no `--mission`.

Schema v4 already keeps every intelligence type in one session table (`observations`, with `category`). Schema v5 would:
- rename that table `items`;
- add `agent_id`, `agent_type`, `mission` and `fields`, and drop `attributed_to`;
- add the types `objective`, `deviation` and `ambiguity`, and drop `finding` (v4 findings become observations, D-SR28);
- fold in the v4 `deviations` table;
- extend `missions` with `agent_id`, `brief_path` and `aar_path`;
- add the verbs `mission update`, `aar` and a per-session `export`.

## Doctrine behind the design (mission 874d-1-aar-doctrine)

Full report, with every quote and URL, read 2026-11-15 on armypubs.army.mil: `.aitools/channel/handoffs/2026-11-15_dbd05b0c-missions/874d-1-aar-doctrine/874d-1-aar-doctrine-report.md` (v1.0, not committed yet). - **Current AAR doctrine is TC 7-0.1, *After Action Reviews* (13 February 2025).** TC 25-20, cited in this issue's v1 question 2, is not on the active list. Agenda (3-2): "Review of objectives and intent." … "Commander's mission/intent (what was supposed to happen)." … "Summary of events (what happened)." … "Discussion of key issues" … "Sustaining / improving performance." Root causes: "Understanding of Root Causes (Why It Happened)" (3-11).
- **Failed objectives are reported at once, then discussed in the AAR, and graded outside it.** At once: "reporting to the commander about the new situation when able to do so" (ADP 6-0, 2026, 1-77), with a "recommended course of action" (1-81). The SITREP line 10 covers "deviations or variations from previously reported intentions or plans" (FM 6-99, 2021, C070). The AAR: "An AAR does not grade success or failure" (TC 7-0.1 3-3). The grade is GO/NO-GO (TC 7-0.1 figure 1-1) or T/P/U (FM 7-0 1-4). Our AAR carries the status itself, because one writer does both.
- **Blocker.** The word appears in none of the eight publications read. The nearest wording is the SITREP's logistics line 12, "problem areas beyond the commander's or service's capability to overcome or alleviate in a timely manner", and the AR 11-33 "Issue", "a … problem that precludes performance to standard". We keep our governed `blocker`.
- **Deviation.** Doctrine's variance is "a difference between the actual situation during an operation and the forecasted plan" (ADP 5-0 4-26), either an opportunity or a threat.
- **Observation.** "Notes or comments on an operation, event, or exercise from the perspective of the person(s) who perceived or experienced it first-hand" (AR 11-33, 2022). Doctrine does not define it by whether anyone acted. The split between acted on and passive is ours (D-SR20).
- **Restating the mission and assumptions.** "the commander/leader restates the mission and intent … Another technique is to have subordinate leaders restate the mission" (TC 7-0.1 3-7). For the running estimate, "Facts and Assumptions", then "MISSION. Show the restated mission" (FM 5-0 table C-1). Ambiguities are resolved before execution in doctrine: "Commanders question contradictory or ambiguous guidance" (FM 5-0 4-42). Recording them in the AAR is our written stand-in for the confirmation brief.

## Open questions

**RFI 874d-4: Should SQLite be the store, written by every agent as described in "Store", with a per-session JSON export as the record that carries forward?**
- The commander leans to SQLite (L565). His main reason for JSON was several writers (L8030: "the multi-writer, without issue? its the main reason to do json"), but one JSON file cannot take parallel writers. SQLite can, and `harness-db.py` already uses WAL, a 5-second busy timeout and `BEGIN IMMEDIATE`.
- March pointed the same way: "sqlite at agentic turns to query the knowledge db and to write to it. not here, in context ... i want to see SOME stuff here" (2026-03-29).
- The session DBs are gitignored (`.gitignore` L66), so only an export carries forward between machines (`.claude/rules/aitools-workspace.md`).

Suggest:
- one DB per top-level session, written by every agent through `harness-db.py`. `--session` is always the top-level session's id. A delegate adds `--mission <its name>`, and harness-db stores the delegate's agentId from `missions` (the table in "Store");
- one `items` table with `agent_id`, `agent_type` and `mission` columns: no `attributed_to`, and no table per agent;
- a per-session JSON export in the schema above, committed at session end, and a short Markdown render in context;
- D-SR7 and D-SR8 then read: "SQLite store, written directly by every agent; JSON export, with a schema and a template".

**RFI 874d-15: What format and location should the brief file have, and do the objectives also stay verbatim in the prompt?**

D-SR27 makes the brief a file that the prompt points to. D-DEL8 says the objectives are verbatim "in the delegation prompt".

Suggest:
- **Format and location.** Markdown, with the schema's node names as headings, filled in from a template, at `<mission directory>/<NAME>-brief.md`. The mission directory is the `/delegate` mission-output directory, `.aitools/channel/handoffs/<date>_<session>-missions/<NAME>/`, and the file takes the D-DEL1 prefix. Markdown reads well line by line, and a hook or a validator can check the headings. The brief's path is recorded in `missions`.
- **Objectives.** The prompt also carries the objectives verbatim, a few lines. They are then in the delegate's context even before it opens the brief, and the hook can verify D-DEL8 from the prompt alone. If you would rather avoid the repetition, D-DEL8 changes to "in the delegation prompt or the brief it points to".

**RFI 874d-16: Should every delegate load `/delegate` at start, so that standing content can leave the brief?**

By the reasoning of D-SR26, content that is the same on every mission does not belong in each brief. That covers `conflict_priority` (D-DEL6), `permissions` (`WRITE_BLOCKED`) and the standing duties: ship your own code, report blockers at once, objectives verbatim down the chain. Today `/delegate` element 3 has the delegate load `/delegate` only "before launching any delegate of its own".

Suggest: every delegate loads `/delegate` at start (element 3). The brief keeps only what is specific to the mission, with `duties[]` listing the duties that apply to this mission.

**RFI 874d-17: Should a governed `deliverable` replace `artifact_refs`?**

`artifact_refs` was meant as pointers to things that are not intelligence items:
- on an objective, the PRs, commits and files the agent produced;
- on a proposal, other material it rests on.

The name is ambiguous. `artifact` is already governed as "a concrete file in the harness that implements a framework or convention", and a PR or a URL is not one (D-SR30).

Suggest:
- **Objectives** get `deliverables[]`: what the agent produced to accomplish the objective, each a pointer a reader can open (a PR or issue URL, a commit SHA, a file path). The writer lists every one. The delegating agent opens each to verify the objective's status (`/delegate` "Verifying what comes back"). `/delegate` already calls the delegate's output its "Deliverable".
- **Proposals** get no extra field. `affected[]` names what they would change, and other material is cited in `why` (L289: "in their fields/body").
- **Glossary.** Govern `deliverable` through `/glossary` with that definition, together with `mission brief` (synonyms: brief, delegate briefing; D-SR18), `after action review` (AAR) and `running estimate`.

**RFI 874d-18: Apply the `/delegate` and rule changes directly now, or with the build?**
