## The design: one schema, three documents (schema v1, proposed)

**One schema.** Every node and every item type is defined once. Wherever a node name appears, it means the same thing. Each document uses the nodes it needs:
- The **mission brief** is what is supposed to happen. The delegating agent writes it before launch, and it is the delegation prompt.
- The **AAR** is what happened against that brief. The delegate writes it at the end.
- The **running estimate** is the session's living record. Every agent writes to it continuously.

The doctrine read by mission 874d-1-aar-doctrine gives the same split:
- the AAR opens with the "Review of objectives and intent", then "what happened", why, and sustain/improve (TC 7-0.1, 2025, 3-2);
- the running estimate holds the facts and assumptions beside the restated mission and is updated as they change (FM 5-0, 2024, table C-1, C-7);
- the brief is the order plus its reporting requirements (ADP 6-0, 2026, 2-77: a CCIR "establishes a reporting requirement").

**`deviation.from.kind`**: what the agent deviated from. It replaces the finding's `criteria_kind`.

| Kind | What the agent deviated from | Example |

| `order` | An order given during the mission, outside the brief: the commander's prompt, or a message from the delegating agent | Told mid-mission to stop pushing; pushed one more commit |
| `plan` | The steps or the sequence of a plan the work follows (`plans/*.md`, a batch plan). This kind is a process deviation (D-SR21) | Ran batch 3 before batch 2 |
| `rule` | A rule, a standing order, a CLAUDE.md file, or a skill's mandated process | Inlined a long Bash command; skipped a mandated skill step |
| `spec` | A specification the work product must meet: a reference document, a schema, an interface contract, a test expectation | Wrote a field the schema does not define |
| `standard` | An outside authority: official tool documentation, a language or style standard, doctrine | Used an install method the official docs do not give |

**`deviation.cause`**

| Cause | Meaning |
|---|---|

### AAR

Written by the delegate at the end and returned as its hand-back. The first three nodes answer "what was supposed to happen" (TC 7-0.1 3-2, 3-7).

```
provenance
  document           aar
  schema_version, version
  session_id
  mission            the delegate's name
  brief_ref          the brief it answers: mission name + brief version
  written_by         {agent_id, agent_type: delegate, name}
  created_at
objectives[]         every objective of the brief, verbatim, + status + how + refs   D-SR19, D-SR23
ambiguities[]        found in the brief, and how each was resolved                    D-SR14
assumptions[]        made or received, each with its end state                         D-SR15
deviations[]         acted on: done differently from the brief, an order, a plan,
                     a rule, a spec or a standard                                      D-SR22
observations[]       seen, not acted on: bugs, issues, incidents, others               D-SR20
operational_learning[]                                                                 RFI 874d-14
proposals[]
rfis[]               open questions, each with a suggested answer
```

The `/delegate` hand-back lines fold into these nodes *(proposed)*:
- `WRITE_BLOCKED` becomes a deviation (cause `blocker`, from a `rule`), already reported at once;
- a `CONFLICT:` line becomes an ambiguity resolved by D-DEL6;
- an `INCIDENT:` marker becomes an observation with `incident: true`;
- PR URLs and files become an objective's `artifact_refs`.

**Blockers in the AAR:**
- the objective's status is `partly` or `not accomplished`;
- a deviation explains it (`cause: blocker`, `from` the objective);
- an assumption is marked falsified, if a wrong assumption was the cause;
- a proposal or RFI, if only the commander can clear it.

### Running estimate

One per session (D-SR8). Written by the session commander and every delegate. Not shared across sessions (D-SR9).

```
provenance
  document           running-estimate
  schema_version, version
  session_id
  maintainer         the session commander
  created_at, updated_at
intent               the commander's intent for the session; main_effort
assessment           is the session proceeding according to the commander's intent?
                     updated every turn (FM 1-02.1 "running estimate"; FM 5-0 table C-1 item 6)
objectives[]         the session's objectives: the commander's orders verbatim + transcript
                     line + status + how + refs
missions[]           the delegation log: mission, agent_id, parent, status
                     (launched | running | returned | failed), brief_ref, aar_ref
facts[], assumptions[], decisions[], ambiguities[]
deviations[], observations[]
operational_learning[]
proposals[]
rfis[]
```

Every item carries `attributed_to` and `agent_type`, so the estimate is the union of what every agent wrote. The brief and the AAR of mission M are the items written for M.

- add the types `objective`, `deviation` and `ambiguity`;
- fold in the v4 `deviations` table.

## Doctrine behind the design (mission 874d-1-aar-doctrine)

Full report, with every quote and URL, read 2026-11-15 on armypubs.army.mil: `.aitools/channel/handoffs/2026-11-15_dbd05b0c-missions/874d-1-aar-doctrine/874d-1-aar-doctrine-report.md` (v1.0, not committed yet). The session commander spot-checked its key quotes from TC 7-0.1, FM 6-99, AR 11-33, ADP 6-0 and ADP 5-0 against the extracted PDF text: all verbatim.

- **Current AAR doctrine is TC 7-0.1, *After Action Reviews* (13 February 2025).** TC 25-20, cited in this issue's v1 question 2, is not on the active list. Agenda (3-2): "Review of objectives and intent." … "Commander's mission/intent (what was supposed to happen)." … "Summary of events (what happened)." … "Discussion of key issues" … "Sustaining / improving performance." Root causes: "Understanding of Root Causes (Why It Happened)" (3-11).
- **Failed objectives are reported at once, then discussed in the AAR, and graded outside it.** At once: "reporting to the commander about the new situation when able to do so" (ADP 6-0, 2026, 1-77), with a "recommended course of action" (1-81). The SITREP line 10 covers "deviations or variations from previously reported intentions or plans" (FM 6-99, 2021, C070). The AAR: "An AAR does not grade success or failure" (TC 7-0.1 3-3). The grade is GO/NO-GO (TC 7-0.1 figure 1-1) or T/P/U (FM 7-0 1-4). Our AAR carries the status itself, because one writer does both.
- **Blocker.** The word appears in none of the eight publications read. The nearest wording is the SITREP's logistics line 12, "problem areas beyond the commander's or service's capability to overcome or alleviate in a timely manner", and the AR 11-33 "Issue", "a … problem that precludes performance to standard". We keep our governed `blocker`.
- **Deviation.** Doctrine's variance is "a difference between the actual situation during an operation and the forecasted plan" (ADP 5-0 4-26), either an opportunity or a threat.
- **Observation.** "Notes or comments on an operation, event, or exercise from the perspective of the person(s) who perceived or experienced it first-hand" (AR 11-33, 2022). Doctrine does not define it by whether anyone acted. The split between acted on and passive is ours (D-SR20).
- **Restating the mission and assumptions.** "the commander/leader restates the mission and intent … Another technique is to have subordinate leaders restate the mission" (TC 7-0.1 3-7). For the running estimate, "Facts and Assumptions", then "MISSION. Show the restated mission" (FM 5-0 table C-1). Ambiguities are resolved before execution in doctrine: "Commanders question contradictory or ambiguous guidance" (FM 5-0 4-42). Recording them in the AAR is our written stand-in for the confirmation brief.
