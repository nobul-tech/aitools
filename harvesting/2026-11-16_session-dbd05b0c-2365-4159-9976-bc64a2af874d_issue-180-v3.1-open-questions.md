## Open questions

**RFI 874d-4: Should SQLite be the store, written by every agent as described in "Store", with a per-session JSON export as the record that carries forward?**
- The commander leans to SQLite (L565). His main reason for JSON was several writers (L8030: "the multi-writer, without issue? its the main reason to do json"), but one JSON file cannot take parallel writers. SQLite can, and `harness-db.py` already uses WAL, a 5-second busy timeout and `BEGIN IMMEDIATE`.
- March pointed the same way: "sqlite at agentic turns to query the knowledge db and to write to it. not here, in context ... i want to see SOME stuff here" (2026-03-29).
- The session DBs are gitignored (`.gitignore` L66), so only an export carries forward between machines (`.claude/rules/aitools-workspace.md`).

Suggest:
- one DB per top-level session, written by every agent through `harness-db.py`. `--session` is always the top-level session's id. A delegate adds `--mission <its name>`, and harness-db stores the delegate's agentId from `missions` (the table in "Store");
- one `items` table with `agent_id`, `agent_type` and `mission` columns: no `attributed_to`, and no table per agent;
- a per-session JSON export in the schema above, committed at session end, and a short Markdown render in context;
- D-SR7 and D-SR8 then read: "SQLite store, written directly by every agent; JSON export, with a schema and a template".

**RFI 874d-15: What format and location should the brief file have, and do the objectives also stay verbatim in the prompt?**

D-SR27 makes the brief a file that the prompt points to. D-DEL8 says the objectives are verbatim "in the delegation prompt".

Suggest:
- **Format and location.** Markdown, with the schema's node names as headings, filled in from a template, at `<mission directory>/<NAME>-brief.md`. The mission directory is the `/delegate` mission-output directory, `.aitools/channel/handoffs/<date>_<session>-missions/<NAME>/`, and the file takes the D-DEL1 prefix. Markdown reads well line by line, and a hook or a validator can check the headings. The brief's path is recorded in `missions`.
- **Objectives.** The prompt also carries the objectives verbatim, a few lines. They are then in the delegate's context even before it opens the brief, and the hook can verify D-DEL8 from the prompt alone. If you would rather avoid the repetition, D-DEL8 changes to "in the delegation prompt or the brief it points to".

**RFI 874d-16: Should every delegate load `/delegate` at start, so that standing content can leave the brief?**

By the reasoning of D-SR26, content that is the same on every mission does not belong in each brief. That covers `conflict_priority` (D-DEL6), `permissions` (`WRITE_BLOCKED`) and the standing duties: ship your own code, report blockers at once, objectives verbatim down the chain. Today `/delegate` element 3 has the delegate load `/delegate` only "before launching any delegate of its own".

Suggest: every delegate loads `/delegate` at start (element 3). The brief keeps only what is specific to the mission, with `duties[]` listing the duties that apply to this mission.

**RFI 874d-17: Should a governed `deliverable` replace `artifact_refs`?**

`artifact_refs` was meant as pointers to things that are not intelligence items:
- on an objective, the PRs, commits and files the agent produced;
- on a proposal, other material it rests on.

The name is ambiguous. `artifact` is already governed as "a concrete file in the harness that implements a framework or convention", and a PR or a URL is not one (D-SR30).

Suggest:
- **Objectives** get `deliverables[]`: what the agent produced to accomplish the objective, each a pointer a reader can open (a PR or issue URL, a commit SHA, a file path). The writer lists every one. The delegating agent opens each to verify the objective's status (`/delegate` "Verifying what comes back"). `/delegate` already calls the delegate's output its "Deliverable".
- **Proposals** get no extra field. `affected[]` names what they would change, and other material is cited in `why` (L289: "in their fields/body").
- **Glossary.** Govern `deliverable` through `/glossary` with that definition, together with `mission brief` (synonyms: brief, delegate briefing; D-SR18), `after action review` (AAR) and `running estimate`.
