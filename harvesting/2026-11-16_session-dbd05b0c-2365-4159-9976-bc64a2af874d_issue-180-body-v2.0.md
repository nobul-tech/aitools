## 1. AAR (after-action review)

### Latest version (D-SR1, D-SR2, D-SR3, D-SR4)

An AAR is a JSON document with three top-level nodes, plus `meta`. The commander set the node names on 2026-03-16 (D-SR1) and renamed the middle node on 2026-11-15 (D-SR2). The three March names (observation, insight, lesson) echo the CALL taxonomy (Center for Army Lessons Learned). Mission fa81-04 found no CALL source to read (`reference/framework-intelligence-types.md` "Not read"), so the names rest on the commander's decisions, not on CALL.

Every entry is an intelligence item of a type defined in `reference/framework-intelligence-types.md` (PR #181), with that file's common and provenance fields (`attributed_to`, `source_kind`, `source`, `quote`, `created_at`). The fields below are what each node adds.

| Node | Meaning | Holds types | Fields (this issue) | Source |
|---|---|---|---|---|
| `meta` | Who, which mission, when | | `mission`, `agent`, `session`, `produced`; `intent_as_understood` if RFI fa81-40 is answered yes | `harvesting/2026-03-22_6_m1-running-estimate-lifecycle-aar.json` |
| `observations[]` | "what happened — facts" | observation, fact, assumption (with its status) | `id` (`OBS-<n>`), `type`, `text`, `evidence`, `severity` (optional), `status` | planning-brief #36 (3); D-SR5; PR #181 |
| `findings[]` | why: the analysis | finding, operational learning (D-SR4) | finding: `id` (`F-<n>`), `observation_refs[]`, `text` (the condition), `criteria`, `cause`, `effect`, `suggestion`, `confidence`, `severity`. Operational learning: `id` (`OL-<n>`), `text`, `finding_refs[]` | D-SR2, D-SR3; GAO elements in PR #181 |
| `proposals[]` | "what to change — with barrier analysis field validating each proposal" | proposal, rfi | proposal: `id` (`P-<n>`), `finding_refs[]`, `what`, `why`, `barrier_analysis`, `severity`, `affected` (files, decisions), `disposition`. rfi: `id` (`<sid4>-<n>`), `title`, `question`, `suggestion`, `answer` | D-SR1; planning-brief #36 (3), #44 (3); D-SR3 |

- **Earlier field names.** The 2026-03-21 delegate AARs (harvested, `harvesting/2026-03-22_6_m*-aar.json`) used `insights[]`, `I-<n>`, `analysis`, `insight_refs[]`, and `fact` for the observation text. D-SR2 and D-SR3 rename them. The harvested files keep their names as history.
- **`finding_refs[]` on operational learning.** The commander asked for `finding_refs[]` on proposals (D-SR3). Giving operational learning the same field follows the reference file's `refs` from an OL to its findings. *(suggested)*
- **`INCIDENT:` and `CONFLICT:`.** These lines and `WRITE_BLOCKED` stay mandatory in the hand-back. An incident is a finding about the harness, tracked in the incident registry (PR #181, "A finding and an incident").

Planning-brief #44 component (3), verbatim: "Each proposal includes: what to change, why, barrier analysis (would this have prevented the issue?), severity, affected decisions".

Planning-brief #36 component (13) (agent-written, status "agreed"): each validated proposal becomes a harness change, a fact in the next brief, an incident (through S2 and S1), or is dismissed.

## Proposed implementation (options)

### Where each schema lives

Each structure (AAR, Mission Brief, running estimate) gets a schema and a template (D-SR7):
- a schema: fields, types, required fields, allowed values;
- a template: an empty instance a writer copies.

| Option | What | For | Against |
|---|---|---|---|
| A | One reference file, `reference/structured-reports.md`: field tables for the AAR, running estimate and briefings, and Markdown templates. `/delegate`, `/handoff` and `/mission-control` point to it | Smallest change; readable in context; D-SR7 allows Markdown | No machine check beyond headings. The running estimate is JSON (D-SR8), so it still needs a JSON template |
| B | JSON Schemas under `registries/` behind a governing skill (three-layer pattern), with a JSON template per structure | Machine-checkable. Matches D-SR8 (the running estimate is JSON) | Every reader and writer goes through the governing skill |
| C | SQLite tables in the harness DB (`scripts/harness-db.py`), each entry an intelligence item with provenance; Markdown renders for context | Matches the March direction (2026-03-28, -29, -30); the intelligence items are already there (schema v4) | Not what D-SR7 and D-SR8 name; the biggest build |

The intelligence items inside these structures use the schema-v4 types and fields whatever the option (PR #181).

### Who produces each, and when

- **AAR**
  - Every delegate at hand-back: the `/delegate` "Final response shape" becomes an AAR.
    - `meta.intent_as_understood`, if RFI fa81-40 is answered yes.
    - `observations`, `findings`, `proposals` (D-SR1, D-SR2), each entry an intelligence item (PR #181), each proposal with its barrier analysis and `finding_refs[]` (D-SR3).
    - What the delegate learns after its merge is recorded the same way, as observations or operational learning (D-SR5). There is no separate section for it.
    - The existing mandatory lines stay: PR URLs, `WRITE_BLOCKED`, `CONFLICT:`, `INCIDENT:`, open questions with suggested answers.
  - The session commander at session end, into the relay entry.
  - A mission commander at mission end, into its mission report.
- **Briefing**
  - The delegating agent writes the Mission Brief (element 10) into every delegation prompt. It is the planning brief that defines the delegate's mission objectives (D-SR12). Suggested fields:
    - Mission objectives.
    - Commander's intent, with directives verbatim and their sources.
    - Mission, scope and exclusions.
    - Situation: facts, assumptions with status, decisions.
    - Coordination: the parallel missions.
    - The return format: the AAR above.
  - The session commander prints a brief to the commander on request, with the 2026-03-26 headings.

- **Running estimate**
  - One per session, as JSON (D-SR8). The session commander and every delegate of that session write to it directly. RFI 874d-1 covers how parallel delegates share the file.
  - Not shared with other sessions (D-SR9). Coordination between sessions through estimates and channels is the roadmap item D-SR10.
  - Updated at each prompt turn (2026-03-21 L1341) and after each delegate returns: the AAR feeds it, per planning-brief #50 (11).
  - Carried forward at session end.

## Open questions

Each stays open until the commander answers it.

**RFI fa81-40: Should a delegate's AAR state the mission as the delegate understood it ("intent as understood")?**

This is question 2, restated. The commander answered "i dont understand the question", so here it is in full.

*What an AAR compares.* An after-action review compares what was supposed to happen with what did happen. The five-part AAR the agent offered on 2026-03-21 (`ab5da7ea` L168) opens with the intent for that reason. The commander's AAR (D-SR1, D-SR2) has three nodes: `observations` (what happened), `findings` (why) and `proposals` (what to change). None of them says what the delegate thought it was supposed to do.

*Why it matters with delegates.* The delegating agent wrote the Mission Brief, so it knows the mission it meant. It does not know the mission the delegate understood. When a delegate misreads its brief, for example by changing the shared rule when it was told to change the skill, its AAR can still be clean: every observation true, every finding sound, every proposal reasonable, but about the wrong mission. The reader finds the misreading only by comparing the work with the brief line by line, after reading the whole AAR. In doctrine, the backbrief has the subordinate restate the mission so that a misreading surfaces early (`reference/framework-mission-command.md` maps the backbrief to checklist item 2). Here the restatement would come at the end, as part of the AAR.

*The question.* Does a delegate's AAR carry that restatement?

- (a) No. The AAR stays as it is, and the delegating agent compares the results against its own brief.
- (b) Yes, as one field in `meta`: `intent_as_understood`, one or two sentences naming the objective and the scope as the delegate understood them. The three nodes stay as they are.
- (c) Yes, as a fourth top-level node before `observations`.

Example of (b):

```json
"meta": {
  "mission": "a1b2-3-aar-schema",
  "agent": "a1b2-3-aar-schema",
  "session": "a1b2c3d4",
  "produced": "2026-11-16T10:00:00Z",
  "intent_as_understood": "Add the AAR schema and template, and make the /delegate Final response shape an AAR. Out of scope: hooks and DB tables."
}
```

Suggest: (b). It keeps the commander's three nodes unchanged, costs the delegate one line, and the reader sees a misread mission before reading anything else.

**RFI 874d-1: How do parallel delegates within one session write the session's JSON running estimate?**

D-SR8 has every delegate edit the session's estimate directly. D-SR9 answers the question between sessions, but delegates of the same session can run in parallel (`/delegate` "Running several delegates at once"). A plain JSON file does not handle that on its own. Each writer reads the whole file, changes it and writes it back, so when two delegates write at once one write is lost, and a crash mid-write leaves a broken file. Does D-SR9's "lets just not worry about that" cover parallel delegates too, or does the per-session estimate need a rule for them?

Suggest: every writer re-reads the file just before writing and replaces it atomically (write a temporary file, then rename it). The file is never left broken. A lost update is still possible, but every item a delegate writes is also in its AAR, so the session commander reconciles the estimate from the AARs when each delegate hands back. No lock and no per-writer files.
