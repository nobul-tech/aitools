Every node and item type is defined once and means the same thing in every document. The **mission brief** is what is supposed to happen; the delegating agent writes it before launch. The **AAR** is what happened against it; the delegate writes it at the end. The **running estimate** is the session's living record; every agent writes to it. Doctrine gives the same split: the AAR opens with "Review of objectives and intent" (TC 7-0.1, 2025, 3-2); the running estimate keeps "Facts and Assumptions" beside "MISSION. Show the restated mission" (FM 5-0, 2024, table C-1); the order carries reporting requirements (ADP 6-0, 2026, 2-77).

**The prompt, around the brief.** The prompt tells the delegate explicitly:
- **Read in full, line by line, before any other work:** the brief; every CLAUDE.md file and rule it lists; the references it lists.
- **Use as reference material, never loaded whole:** the chain-of-command transcripts (`provenance.chain_of_command`), read with `read-session.py` or `read-session-full.py`, the commander's prompts newest first, whenever a question comes up; large registries, reports and extracted documents, searched for what the mission needs.

**Blockers in the brief:** none. Reporting a blocker at once is a standing duty (D-DEL9). A blocker already known at launch is written as a constraint, or in the prompt body, and the objective it affects says so.

The hand-back's free-text lines fold into these nodes (D874d-29, D-DEL11):
- `WRITE_BLOCKED` becomes a deviation (cause `blocker`, from a `rule`), already reported at once;
- a `CONFLICT:` line becomes an ambiguity resolved by D-DEL6;
- an `INCIDENT:` marker becomes an observation with `incident: true`;
- PR URLs and files become an objective's `deliverables`.

**Blockers in the AAR:**
- the objective is `partly` or `not accomplished`;
- a deviation explains it (`cause: blocker`);
- an assumption is marked falsified, if a wrong assumption was the cause;
- a proposal or RFI, if only the commander can clear it.

**How a delegate learns its own agentId (D874d-33).** `/delegate` "Claude Code specifics" documents two ways:
- a `TaskStop` error, which names the caller's own id ("Task … is owned by …; agent <my id> cannot stop it");
- the parent session's transcript, searched for its `"agentId"` next to its mission name in the `description`.

This is for the **Claude Code harness**. Other harnesses (Claude Code web, Cursor CLI, Cursor cloud agents) need to be examined. One observation: the `.meta.json` that links a mission name to its agentId was created when delegate 874d-1-aar-doctrine finished (20:55:18Z), not at launch, so it is no help while a delegate runs.

**The mission commands are withdrawn.**
- What they were: `harness-db.py mission start | update | end`, run with Bash by the delegating agent, to keep a `missions` table (name, parent, brief path, agentId, status).
- Why they were proposed: only because a running delegate could not be sure of its own agentId.
- Why they are gone: with D874d-33 each delegate writes its own `agent_id`. The brief file (named by the mission, D874d-42) and the delegate's own rows already carry the rest, so the estimate's `missions[]` is derived on export.

**Schema 5** (a code change, with a migration and tests):
- rename the v4 session table `observations` to `items`;
- add `agent_id`, `agent_type`, `mission`, `fields`, and drop `attributed_to`;
- add the types `objective`, `deviation`, `ambiguity`, and drop `finding` (v4 findings become observations, D874d-28); `fact` stays (D874d-43);
- fold in the v4 `deviations` table;
- replace `--session` with `--db`;
- assign item ids on insert;
- add an `aar --agent-id <id>` verb, which renders a delegate's rows as its AAR, and a per-session `export`.
