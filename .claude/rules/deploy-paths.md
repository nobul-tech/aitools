## Deployment Paths (this repo)

Three parallel deployment paths must produce equivalent results. The dev and
MDM paths stay as they are; the package path is added beside them
(commander, 2026-10-26):

1. **Dev/repo path** (`scripts/setup-*.sh/.ps1`): reads `shared/` and user repo at
   runtime. Used by `aitools` CLI.
2. **MDM path** (`<userRepoPath>/deploy/setup-*.sh/.ps1`): self-contained, personalized,
   generated by `build-deploy.sh` into the user's dotprofile repo. Used for endpoint
   deployment. The shared `aitools/deploy/` is frozen (no longer regenerated).
3. **Package path** (`scripts/build-package.sh`): installable packages for a fleet of
   users: a Windows Intune Win32 app (`.intunewin`), an unsigned macOS PKG (Intune,
   Jamf) and a Linux `.deb` for Ubuntu 24.04 and 22.04 (VMs and containers,
   including Claude Code web and Cursor cloud). The payload is the aitools tree at
   a pinned ref (`git archive`), never the dotprofile `deploy/`; the package runs
   the dev-path scripts from it (`scripts/aitools-install.*`), so it adds no third
   copy of setup logic. `build-package.sh` never calls `build-deploy.sh`. No
   personal data goes into a package. Design: `@plans/build-package/design.md`.

### Equivalence

For the same platform, environment and profile, all three paths leave the same
end state: the same files under `~/.aitools`, `~/.claude` and `~/.cursor`, and the
same managed-tool states and summary rows. The package path holds this by
construction (same scripts, same order). Where a package user has no dotprofile,
only the profile-sourced content differs (the neutral fleet template, design.md
"Personalisation per fleet user"),
and the run says so in its summary; it never silently uses another profile.

### MDM run order

`deploy/deploy-harness.sh/.ps1` runs first: it fills `~/.aitools` (rules,
reference, registries, hooks, skills, bin, config.json), and the rules fan-out
in `setup-user-cursor` (and `setup-user-claude` once it fans out) reads
`~/.aitools/rules`. Run in the other order, the fan-out step reports
`n/a (no harness rules)` and deploys nothing.

`deploy-harness` ships with its `deploy/` directory: its config.json writer
(`setup-user-config`, `aitools-profile`, `aitools-json`) sits beside it. As on
the dev path, the writer needs the installer's bootstrap keys (`reposPath`,
`repoPath`) in `~/.aitools/config.json`; on an endpoint where `aitools-install`
has not run, the harness files still deploy but the run reports
`ERROR config.json not generated` and exits 1.

### When changing `shared/` content

1. Edit the `shared/` source file
2. If the file has a user repo counterpart (e.g., `@shared/claude-shared.md` →
   `<userRepoPath>/claude/CLAUDE.md`), update both
3. Run `bash scripts/build-deploy.sh` to regenerate `<userRepoPath>/deploy/` (your dotprofile repo)
4. The dev and MDM paths now produce equivalent output; the package path picks the
   change up when built from a ref that contains it

### When changing `scripts/setup-*.sh/.ps1`

1. Edit the `scripts/` source
2. Run `bash scripts/build-deploy.sh` to regenerate the `<userRepoPath>/deploy/` counterpart
   (it takes the dotprofile from `AITOOLS_USER_REPO_PATH`, else from the resolver;
   an agent runs it only under an isolated `HOME` with a copy of the dotprofile:
   it deletes and rebuilds `<dotprofile>/deploy/`)
3. Verify the dotprofile `deploy/` includes the change (the shared `aitools/deploy/` is frozen, so pre-commit deploy-drift steps 3+10 no longer apply to it)
4. If the script runs on the package path (every script `scripts/aitools-install.*`
   runs), run `bash scripts/build-package.sh stage` and verify the staged payload
   contains the change (from batch B2 of `@plans/build-package/implementation-plan.md`;
   until then `stage` is a stub that exits 1, and `--dry-run` shows the plan)

### Template sync

`@shared/claude-shared.md` and `<userRepoPath>/claude/CLAUDE.md` must stay in sync.
When one changes, update the other. The user repo template takes priority at runtime
(scripts/ path reads it first, falls back to shared/).

### Scripts with deploy templates (duplication risk)

One script pair has **duplicated setup logic** between `scripts/` and
`build-deploy.sh`. Fixing a bug in it requires manually porting to the other.
Running `build-deploy.sh` does NOT auto-fix stale template logic — it faithfully
reproduces whatever is hardcoded in the template.

| Script | What's duplicated |
|--------|-------------------|
| `setup-user-hooks.sh/.ps1` | Hook-script embedding + REGS_JSON injection (build-time self-containment; the settings.json hooks merge itself is extracted, not duplicated) |

These pairs are **pure extract** (body markers + `inline_lib_*`) — no duplicated
logic:
- `setup-user-mcp.sh/.ps1` and `setup-user-settings.sh/.ps1`. The settings.json
  merge formerly duplicated in `setup-user-mcp` was removed in the settings-sync
  refactor (`sync_managed_json` now owns settings.json).
- `setup-user-claude.sh/.ps1` (M3 B5): template interpolation, footer, managed-file
  deploy and rules logic are extracted from `scripts/`. `build-deploy.sh` adds only
  the profile/template source block (the live dotprofile on the machine wins, else
  the embedded build-time copies) and the rules fallback.
- `setup-user-cursor.sh/.ps1` (M3 B5): the whole cursor body is extracted; only the
  two preference defaults in the profile preferences block are replaced with the
  build-time `profile.json` `cursor.cli` values (the fallback when the machine has
  no dotprofile).

Every resolver-consuming deploy script (`setup-user-claude`, `-settings`,
`-cursor`) resolves the dotprofile (`setup-user-claude` also this machine's
profile) when it runs, never at build time: no machine's values are interpolated
into `deploy/`.

`deploy-harness.sh/.ps1` is **extract + embed**: `build-deploy.sh` extracts its
code between its section headings (`extract_span`, each heading must match one
line) and replaces only section 2 (dotprofile lookup) with the embedded
snapshot; the source directories and bin CLIs are parsed from its
`add_source` / `for cli in` lines, not listed twice. Renaming a section
heading or rewording those lines fails the build loudly.
`setup-user-config`, `aitools-profile` and `aitools-json` are copied as-is
(library inlined) so `deploy-harness` reaches its config.json writer.

**What IS auto-embedded** (safe — single source of truth):
- `shared/hooks/*.sh` → read via `cat` at build time
- `shared/skills/*.md` → read via `cat` at build time
- `<userRepoPath>/claude/CLAUDE.md` (else `@shared/claude-shared.md`) → read at
  build time, tokens left in place (the fallback template; resolved at runtime)
- `<userRepoPath>/profile.json` → its snapshot (`aitools-json.pl snapshot`:
  version, identity, cursor, profiles), the fallback when the machine has no
  dotprofile
- `<userRepoPath>/claude/rules/*.md` → read at build time (the fallback rules)
- `scripts/aitools-profile.sh/.ps1`, `scripts/aitools-lib.sh/.ps1`,
  `scripts/aitools-json.pl/.ps1` → copied at build time into the resolver-consuming
  deploy scripts and written to a temp dir at runtime (`AITOOLS_PROFILE_SH` /
  `AITOOLS_PROFILE_PS1`); a file the resolver loads that the embed does not carry
  fails the build
- Every `scripts/deploy-harness.*` source (`reference/`, `registries/`,
  `shared/hooks`, `shared/skills`, `.claude/skills`, `shared/rules`,
  `.claude/rules`, `<userRepoPath>/claude/rules`, the bin CLIs) → its
  `git ls-files` list and contents, embedded as base64 at build time

`check-pre-push` step 7 rebuilds into a temp copy of the dotprofile and dry-runs
the generated resolver consumers, so a deploy script that cannot find its resolver
fails the push, not an endpoint.

**When changing setup logic in the script above** (`setup-user-hooks`):

1. Fix the bug in `scripts/setup-*.sh` and/or `.ps1`
2. **Find and fix the same logic in `build-deploy.sh`** (search for the function
   name, variable name, or pattern)
3. Run `bash scripts/build-deploy.sh`
4. Verify `deploy/` output contains the fix (not just the old template output)
5. Pre-commit step 13 will warn if step 2 was missed

This duplication is a known technical debt item (incident I6, see ROADMAP.md).
The structural fix is to refactor `build-deploy.sh` to extract setup logic from
`scripts/` at build time instead of maintaining parallel copies.
